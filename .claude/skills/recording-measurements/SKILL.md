# 実測を記録する

## 原則

**このプロジェクトの数値はすべて実測である。** 推測は数値として書かない。

訂正は 64 件（`docs/decisions.md` C-001〜C-064）。**ほぼ全部が同じ形**:
**1 コマンド打てば分かることを、打たずに推論した。**

残りは 3 つの別の形をしている。これも同じくらい踏む:

| 形 | 例 |
|---|---|
| **n=1 の値を代表値にした** | EMA 差「12.53 dB」は n=1 かつ退化入力での値。実文では 14.5 dB (C-017) |
| **単位を混ぜた** | トークン / 音素 / 符号化後 ID の 3 つを取り違えて「306 vs 116」の論争になった (C-019) |
| **「無い」を測らずに書いた** | 「SCOREQ の pip パッケージが無い」→ PyPI に普通にあった (C-016) |

## 書く前のチェック

数値・サイズ・能力の主張を書こうとしたら、必ず自問する:

1. **これは自分で実行して観測したか？** していないなら測る
2. **測ったなら、再現コマンドを書けるか？** 書けないなら記録として不完全
3. **`measured` か `estimated` か明示したか？** 概算を実測のように書かない
4. **n はいくつか。単位は何か。** n<10 なら n と CI を必ず併記する。
   「〜が〜より大きい」を n=3 で書かない（C-004 / C-017）
5. **「無い」「できない」も主張である。** 探した範囲を書く（C-016）

**「無い」の測り方**（1 コマンドで済むことが多い）:

```bash
curl -s https://pypi.org/pypi/<pkg>/json | head -c 200   # パッケージの存在
grep -rn "<symbol>" <path>                               # シンボルの存在
uv run python -c "import x; print(x.__file__)"           # import できるか
```

## 記録の形式

`docs/measurements.md` に追記する。**全項目に再現コマンドを付ける。**

```markdown
## M-NN. 見出し（自己実測 / ワークフロー報告値 のどちらか明記）

再現:
​```bash
uv run python - <<'PY'
...
PY
​```

出力:
​```
（実際の出力をそのまま貼る）
​```

| 項目 | 値 |
|---|---:|
| ... | ... |

⚠️ 未検証の部分があればここに書く
```

そのうえで:
- 概算しか出せないなら **⚠️ とともに「実測ではない」と明記**
- 他エージェントの報告値なら **「私自身は再検証していない」**と書く
- 数値が既存の記述と食い違ったら、古い方を**訂正記録 C-NNN として残す**（消さない）

## 危険信号 — この考えが浮かんだら測る

- 「ファイル名から明らかに〜だろう」→ C-002 の入口
- 「著者／出自から考えて〜のはず」→ C-003 の入口
- 「config が一致するから同じ」→ C-005 の入口
- 「言語学的に考えて〜」→ C-004 の入口
- 「⚠️ 未検証と書いておけば数字は載せてよい」→ **C-009 の入口。注記は免罪符にならない**
- 「ディレクトリサイズを見た」→ 内訳を見ていない。C-008 の入口
- 「探したが見つからない」→ **探した範囲を書いていない。C-016 / C-024 の入口**
- 「固有名詞から URL やパスを組み立てた」→ **綴りを一次ソースで確認したか。C-024 の入口**
- 「暫定値として 1.0 を置く」→ **値を決めていない状態を隠している。C-021 の入口**
- 「外挿せず実測した」→ **測った対象は本番と同じか。C-046 の入口**
- 「コードのコメントに制約を書いた」→ **それも主張。測っていないなら『未検証』と書く**
- 「n は小さいが傾向は明らか」→ C-004 / C-017 の入口。**傾向は CI で語る**
- 「この 2 つの数字はどちらが正しいのか」→ **単位が違う可能性。C-019 の入口**
- 「手元で打ったら通った」→ **読者の環境には無いものが入っている。C-040 の入口**
- 「依存を外した環境で通った」→ **本当に外れているか数えたか。C-041 の入口**
- 「同じ数字が 3 か所にある」→ **定義が違う可能性。C-042 の入口**（テーブルサイズが 4 通りになった）
- 「`import` 名がこれだから上流はこれ」→ **配布名は別物。C-048 の入口**
  （`import pyopenjtalk` の実体は `pyopenjtalk-plus`。34 中 22 ファイルが違った）
- 「A の N% が B で覆える」→ **A と B が同じ集合か。C-051 の入口**
  （「辞書に無い token」と「未知語ノードになる token」は数が近いが中身が違う）
- 「この段は 4 つ」→ **全部で何段あるか数えたか。C-049 の入口**
  （移植した 4 段はホスト既定 7 段のうちの 4 つだった）
- 「命令数が減った」「マイクロベンチで速かった」→ **実機で測ったか。C-055 の入口**
  （命令数 70 → 59 で、実機は 2 倍遅くなった）
- 「n は書かなくても比だけで足りる」→ **C-059 の入口。** n=298 と n=1,495 で 2 倍違った
- 「安全側に倒してある」→ **どちらが安全側か式で確かめたか。C-064 の入口**
- 「再現コマンドを機械的に走らせよう」→ **副作用を読んだか。** 実際に共有の成果物を壊した（下記）
- 「0 だった」「差が出なかった」→ **陽性対照を先に通したか。**
  実際に `lru_cache` で陽性対照ごと 0 になっていた（M-70）

## 上流の申告値を自分の実測と混ぜない

公式実装 `Ampixa/sanoTTS`（GPL-3.0）の公開ドキュメントには実測値が載っている。
**参照してよい**（数値・ハイパーパラメータ・構成は事実で著作権の対象外）が、
**うちが再現したわけではない。**

| 置き場所 | 中身 |
|---|---|
| `docs/measurements.md` の **M-番号** | **自分で実行して観測した値だけ** |
| `docs/upstream-sanotts.md` | **上流の申告値。全項目「未再現」と明示** |

**混ぜると「ESP32 で 0.22× RT が出た」と読める記述ができあがる。**
うちの実測は CoreS3 で **0.446× RT**（M-90。満チャンク 1 pull。発話全体では 0.541〜0.712）で、
0.22 は上流の申告値のまま。**上流がどちらの定義で測ったかは公開されていない**ので、
「何倍遅い」を書くときは**自分の定義を必ず添える**。
実機が初めて動いたのは 2026-09-02（M-82、当時 0.926）で、それ以前の文書は「実機未」の状態で書かれている。

⚠️ **ソースコードは読まない**（GPL-3.0 が MIT に伝播する）。
hook が `gh api .../contents/*.c` や `git clone` を deny する。
**ドキュメントの取得は通る。**

## 速度は実機でしか測れない — 命令数もマイクロベンチも予測しない（C-055）

**「速くなった」と書いてよいのは、その形のコードを実機で測ったときだけ。**
2026-09-03 に GELU の最適化（S2 計画 T5）で踏んだ:

| 根拠にした手段 | 出た値 | 実機 |
|---|---|---|
| objdump の命令数 | 70 → **59**（減った） | **118 → 211 cyc/要素**（2 倍遅い） |
| QEMU の checksum | 基準と bit 一致 | 値は正しい。時間は分からない |
| マイクロベンチ（pie_probe E 節） | 112 → **74.5 cyc/要素** | **測ったのは旧形**。新形は測っていなかった |

原因は `x < 0 ? -y : y` を符号ビットの `memcpy` に置き換えた 1 か所で、
GCC 14.2 for Xtensa が FP ↔ 整数の往復を**スタック経由の store → load** に落とし、
in-order の LX7 が要素ごとに止まっていた。**依存による停止は命令数に出ない**（M-87 / C-055）。

- **QEMU の割合も命令数も実機の速度を予測しない**（M-80 → M-82 でも同じ形を踏んでいる）
- **マージ直後に `-DSAAN_PROFILE=1` の表を、前の版と 1 行ずつ並べる。** 段の行を見れば 10 秒で分かる
- **マイクロベンチには「これから入れる形」を先に足す。** 入れてから測るのは順序が逆
- 実装者の notes の「⚠️ 残る無駄」は、成果より先に読む（今回は答えが書いてあった）

## 再現コマンドは副作用を持つ — 走らせる前に出力先を読む

**M 番号の再現コマンドを機械的に走らせたら、リポジトリを壊した**（M-102）。

| 走らせたもの | 何が起きたか |
|---|---|
| M-41 の `export_c_weights.py --ckpt runs/v2/stage4.pt` | **既定の出力先が `csrc/`** なので、出荷している `student.bin` / `golden.bin` / `export.json` が**v2 に戻った**。記録としては正しいコマンドで、壊れたのは作業ツリーの方 |
| M-55 の `make int8-e2e CFLAGS_EXTRA=-DSAAN_INT8_ACT=1` | W8A8 のバイナリが残り、**次の素の `make` が作り直さずに再利用**。SNR 28.11 → 24.23 dB |

⚠️ **どちらも `make -C csrc all-test` が落ちて初めて気づいた。**
気づかなければ、次のリリースに v2 の重みが載っていた。

- **走らせる前に、そのコマンドの既定の出力先を読む**（`--out` の default）
- **古い ckpt を指す再現コマンドは、出力先をそらして走らせる**
  （`--out /tmp/repro --report /tmp/repro/export.json`）。
  **hook が既定の置き場への上書きを deny する**（`check_stale_ckpt_export`）
- **一括で走らせるなら、先に `git status` を取り、後で差分を見る**

⚠️ **自分のハーネスの不備を、対象の欠陥として報告しかけた**（M-102 §2。2 回）。
`$PY` を各フェンスの外で定義していたので rc=127 が並び、
**「再現コマンドが 4 件壊れている」**と読めた。実際は 0 件だった。
**一括実行の結果が「大量に壊れている」なら、まずハーネスを疑う。**

⚠️ **「再現コマンドが無い項目が 34 件」も私の数え間違い**だった。
` ```bash ` しか数えず、` ```python ` / 素のフェンス / インラインのバックティック /
「再現:」の行を見落としていた。**実体は 3 件。**

## 100% は疑う

`kana_g2p` の往復テストで最初に出た **100% は、59.5% の文を除外した結果**だった。

分母を必ず確認する。**カバー率と精度は必ずセットで報告する。**

```
✗ 往復一致 100%
✓ 表現可能 96.40% / そのうち往復一致 100.00%
```

同じ理由で、held-out で測る。語彙を作ったテキストで精度を測れば当然 100% になる
（論文が narrow test set で SCOREQ を 1.35 過大評価した構図と同じ）。

## ゲートを通ることは正しさの証明ではない

`gen_teacher_labels.py` は 13 個のゲートを持つが、TSV のヘッダ行がそのまま
発話として通っていた（`uid="id"` / `text="text"`、C-018）。「テキスト」は
日本語として読めるので、長さも速度も音量も全部正常だった。

**ゲートは「値がおかしい」を捕まえる。「行が実データでない」は捕まえられない。**
入力の読み込み側でしか防げない。同じ理由で:

- 「全部 PASS した」を「正しい」と書かない。**何を見ていないか**を併記する
- 出力の先頭 1 件を必ず目で見る（`seq=0` を見れば一発で分かった）
