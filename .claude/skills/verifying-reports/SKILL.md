# 他者の報告を受け取る

## 原則

**報告は仮説であって観測ではない。** 自分で走らせるまでは「そう報告された」としか書けない。

このプロジェクトで実際に起きたこと: 8 件の実測タスクに検証を付けたところ、
**5 件で実質的な誤りが見つかった**。どれも報告自体は自信を持って書かれていて、
数値も自己整合していた。

| 見つかった誤り | 性質 |
|---|---|
| 生徒の SCOREQ 目標 1.29 | 論文の**UTMOS 比 0.6335** を SCOREQ に適用していた（正しくは 0.5427 → 1.112） |
| 「M-2.5 の 12.53 dB は再現しない」 | **再現した。** 元スクリプトを走らせれば出る（n=1 の退化入力での値だっただけ） |
| 「上限 95 dB」 | 発話全体の値。**学習が使う 32 フレームセグメントでは 33.6 dB** |
| 「spectral は 15% 分離が遅い (p=0.055)」 | 別 split では消える (p=0.77)。**しかも検定の選択も誤り**（対応ありなら p=0.0050） |
| 「最終フレームの勾配が常に無音を出せになる」 | `F.pad` の 0 は定数で**そもそも勾配経路が無い** |

**2026-08-28 にワークフロー 3 レーンを敵対的検証したところ、
1 レーンが PARTIAL、2 レーンが CONFIRMED だったが、
CONFIRMED のレーンからも「未報告の交絡」が出た。**

| 見つかった誤り | 性質 |
|---|---|
| 「int8 コアが参照と一致することの**証明**」 | 数値は完全一致したが、**合否は Pearson だけ**で SNR を見ていなかった。「証明」は成立しない |
| 「fp32 比 25 dB を満たす」 | **判定式が後から緩められていた**（指定は「≥25 dB」、実装は「平均 ≥25 かつ最小 ≥23」）。実測の最小は 23.27 dB で 24 文中 9 文が 25 dB 未満 |
| 「アクセントの符号一致 35/36」 | 数値は再現した。⚠️ ただし **pyin を yin に替えると 28/36 に落ちる**（結論の向きは保たれる）。**推定器依存が未報告** |
| 「レイテンシ 1.11 倍」 | 再実行すると 1.064 倍。**向きは再現、大きさは再現しない**（ホスト計時なので当然だが、docs には 1.11 と書かれていた） |
| 「`make arena` が claim の数値を測定している」 | **printf のハードコード文字列**で、実行時に計算していなかった |

## 受け取ったらやること

**1. `repro` を実際に走らせる。**

再現しないなら、それが最重要の指摘。再現したなら「JSON の何フィールドが一致したか」を書く
（壁時計時間だけ違うのは正常）。

**1.5 ゲートが空虚でないか確かめる。**

**報告が引用している「OK」が、何も測っていないことがある。** 実際にあった形:

- **合否に入っていない数値を根拠にしている** — 表示されている SNR が `printf` だけで、
  判定は Pearson（スケール不変）だった
- **同じ入力を 2 回渡しても通る** — `./int8_e2e_test a.bin a.bin …` が「平均 inf dB / OK」
- **しきい値が実測に合わせて後から決められている** — 回帰検出には使えるが合格基準ではない
- **指定したゲートが勝手に緩められている** — 満たさなかったのに OK が出ている

**確かめ方は 1 つ: 壊して落ちるか見る。** 同じ引数を 2 回渡す、層を 1 つ抜く、
しきい値の直下の値を入れる。落ちなければ、そのゲートは根拠にならない。
書く側の観点は [`writing-gates`](../writing-gates/SKILL.md)。

**2. スクリプトを読む。** 特にこの 4 つ:

- **フレームとサンプルの対応**を取り違えていないか（hop 256、`ceil(dT)`、`round` ではない）
- **指標が推定器に依存していないか**（F0 なら pyin / yin を入れ替えて結論が保つか）
- **スケールを二重に掛けて**いないか（int16 / 32767、fp16 の丸め）
- **n が結論を支えるか。** CI を書かずに差を主張していないか
- 「教師と一致」と書いてあるなら、**本当に bit 一致を見ているか**

**3. 結論がデータから出ているか、実験設計から出ているかを判定する。**

これが一番見落とされる。実際にあった例:

> 「L2 項は誤差構造を見ていない（弁別力 1.00）」

→ 正規化関数が誤差 RMS を厳密に揃えていたので **L2 が定数になるのは自明**だった。
データではなく実験設計から出た結論（**循環論法**）。

> 「λ₂ は誤差レベルに厳密に反比例（8.00 倍）」

→ 誤差レベルを 0.05 と 0.40 に設定したので **0.40/0.05 = 8**。ただの算術。

**3.5 「速くなった」の根拠が実機かを見る。**

報告の主な成果が **objdump の命令数 / QEMU のサイクル / ホストのマイクロベンチ**なら、
**速度の主張としては採用しない**。2026-09-03 に通してしまった形（C-055 / M-87）:

- 報告: 「FP 分岐 2 つを消して命令数 70 → 59。QEMU checksum は bit 一致」
- 実機: **GELU が 118 → 211 cyc/要素**（2 倍遅い）。1 step が 14.7% 遅くなっていた
- ⚠️ **実装者の notes には「残る無駄: 符号の bit 演算がスタック往復に落ちている」と書いてあった**

→ **報告の「⚠️ 残る無駄」「未解決」の欄を、成果の欄より先に読む。**
→ 速度は**マージ直後に実機の `-DSAAN_PROFILE=1` の表を前の版と 1 行ずつ並べる**まで確定しない。

**4. 「未検証」と書かれた箇所を 1 つ実測する。**

報告が自分で「推測」と認めている箇所は、たいてい当たっていない。
今回も「n_fft の効きはビン数が主因と推測」が外れた（51% しか説明しない）。

## 書き分け

| 状態 | 書き方 |
|---|---|
| 自分で走らせて再現した | 通常どおり数値を書く |
| 報告を読んだだけ | **「私自身は再検証していない」**と明記する |
| 再現したが解釈が違う | 数値は採用し、**解釈だけ差し替える**（今回 5 件ともこの形だった） |

## 決定は生き残ることが多い

上の 5 件はすべて**根拠が崩れたが決定は維持**された。
「報告に誤りがあった＝結論も間違い」ではない。

**やるべきは、docs に転記する根拠を差し替えること。**
崩れた根拠をそのまま決定記録に載せると、後から読んだ人が
それを信じて次の判断をする（このプロジェクトが C-009 で実際に踏んだ形）。

## 自分の報告を書くとき

受け取る側が上をやれるように書く:

- `repro` に**そのまま実行できるコマンド**を入れる
- 「未検証」「外挿している」を**caveats に分けて書く**（本文に埋めない）
- n が小さいものは **n と CI を数値の隣に**書く
- **測っていないことを「差が無い」と書かない**（「n=24 では検出できない」）
