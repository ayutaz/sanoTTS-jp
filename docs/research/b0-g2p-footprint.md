**このレポートの数値の扱い**

- 表の `measured` 行は実際に辞書をビルドして `stat` し、実際に G2P を通した値。`estimated` 行は算術のみ。

## 1. 結論

**ESP32-S3 に日本語 G2P の「フル辞書相当」は載らない。枝刈り辞書路線は目安 95% に到達しない。**

| 問い | 数字での答え | 出所 |
|---|---|---|
| 16 MB ボード + OTA 2 枠の辞書予算に収まる最大の辞書は？ | **11.6–11.7 MB / held-out 文単位 音素列一致 73.0–73.4%** | 独立 2 系統の実ビルドで一致（§2） |
| 95% に届く辞書サイズは？ | **400,000 entries = 41,995,303 B (40.05 MiB)** で音素列 95.53%。**32 MB ボードにも入らない** | b0_size.json（実ビルド） |
| アクセント込みで 95% に届くか？ | **届かない。** 400k / 40 MiB でも (P3,A1,A2,A3) 一致は **89.29%** | b0_size.json（実ビルド） |
| そもそも辞書を全部載せれば解決するか？ | **しない。** MCU に載せられる C 実装のみの経路（pyopenjtalk-plus の Python 後処理層を外す）では、**フル 103 MB 辞書でも**教師とのアクセント句一致は **76.22%**、音素列一致 94.67% | 検証パスの実測（held-out 2,325 文, use_vanilla=True） |

補足すると、上の 73% という数字自体が**達成不能な上界**である。測定は全部 `pyopenjtalk`（= pyopenjtalk-plus 0.4.1-post8）の既定経路で行っており、その Python 後処理層は SudachiDict-core 209 MB と nani ONNX に依存する。ESP32 には載らない。C 実装だけに落とした時点で、辞書サイズと無関係に held-out の 23.78% でアクセント句が教師と変わる。

一方で**判定が指標の定義に依存する**ことは明記しておく。計画書 §1.5 の受け入れ条件「一致率が実用水準（目安 95%+）」は文単位か音素単位かを規定していない。同じ測定を音素（トークン）単位で読むと 30k 表層形 / 7.13 MB で PER 3.24% = 96.8%、60k / 12.13 MB で 97.4% となり合格する。本レポートは計画書の文言「実文の何 % が正しく読めるか」に従って**文単位**を主指標に採ったが、これはユーザーが確定すべき論点である（§8）。

**推奨する落とし所**（詳細は §4）:

- **蒸留の入力境界を音素ID列に置く**（論文 §II と同じ境界、"external G2P excluded"）。ホスト側 G2P なら端末フットプリント 0 B・精度は教師と同一・回線 68 B/文。音声を Opus で流すより 2 桁安いので、「端末で合成する」ことの利点（帯域・遅延・オフライン再生）は失われない。
- **完全スタンドアロン用途は定型文プリコンパイル**で埋める。1 B/音素で通知系 40.4 B/文、1,000 文で 40 KB。同じ文を PCM で焼くより 3,228 倍小さい。
  ただし「0〜100 × 24 助数詞の数値スロット 41.4 KiB」案は**反証済み**（テンプレートに差し込むと 36.1% が壊れる、§7）。テンプレート × スロット値の組で事前コンパイルする必要がある。

## 3. 判定

### 判定: **入力境界の再定義**（プロジェクト続行、ただし G2P は端末外）

計画書 §1.5 の分岐は「一致率が実用水準（目安 95%+）で数 MB に収まる → 続行 / 収まらない → 入力境界の再定義」。**収まらない。**

理由（すべて実測）:

1. **数 MB では届かない。** 5.9 MB で 68.9%、7.66 MB で 69.7%、11.7 MB で 73.4%。95% には 42.0 MB 必要で、これは最大構成の ESP32-S3（32 MB flash / OTA 2 枠 = 27.19 MiB）にも物理的に入らない。
2. **アクセントは 95% に一度も到達しない。** 42.0 MB でも (P3,A1,A2,A3) 一致は 89.29%。教師の duration predictor は A1/A2/A3 を直接読む（`piper_plus_g2p/japanese.py:32`）ので、ここのズレは蒸留ラベルの品質に直結する。
3. **辞書を全部載せても足りない。** MCU に載る C 実装だけの経路では、フル 103 MB 辞書でも held-out のアクセント句一致は 76.22%（音素列 94.67%）。差分は pyopenjtalk-plus の Python 後処理層に由来し、うち `modify_kanji_yomi` は SudachiDict-core 209 MB に依存する。**これは辞書サイズを増やしても消えない床である。**
4. **B-0 の本題の半分が未測定なので、続行判断を flash だけで下すことはできない。** RAM ピーク・レイテンシ・xtensa ビルドは一切測っていない（§7）。仮に上の 1–3 が全部クリアされても、ここで落ちる可能性が残っている。

一方、**プロジェクト自体の見直しは不要**。入力境界を音素ID列に置けば（論文自身がそうしている）、G2P のフットプリント問題は消え、蒸留の実装に進める。ESP32 で「日本語が喋れる」という要件は、音素ID列を受け取って合成する構成で満たせる（§4 案4 + 案2）。

**ただし判定に付く条件が 2 つある**（ユーザー判断が必要、§8）:

- **「95%」を文単位ではなくトークン単位で定義するなら判定は変わる。** 30k / 7.13 MB で PER 3.24%（96.8%）、60k / 12.13 MB でアクセント記号込み PER 3.99%（96.0%）。この読みなら「数 MB で 95%+」は成立し、続行になる。
- **OTA を要件から外すなら 16 MB ボードの予算は 13.19 MiB になり**、60k full（12.13 MB / 72.3%）まで入る。予算 11.19 MiB は OTA 2 枠を仮定したシナリオ B の値であって固定値ではない。

| 16 MB / A | 13,828,096 | 13,815,068 | 76.04% |
| 32 MB / B | 28,508,160 | 27,607,296 | 91.31% |

補足（すべて measured または明示の算術）:

- **MMU 制約**: ESP32-S3 は 512 エントリ × 64 KB = **同時に 32 MB しかマップできず**、flash と PSRAM が同一 vaddr プールを共有する。数 MB の辞書には影響しないが、32 MB flash + 16 MB PSRAM 構成では flash 側が約 16 MB に制限される。
- **flash mmap でのランダム読みは production 実績がある**。Espressif 自身のオンデバイス中国語 TTS（esp-skainet chinese_tts）が 3,890 KB の voice_data を `esp_partition_mmap` して生ポインタで読んでいる。論文の「SIMD オペランドを flash マッピング経由で読むと相関 0.011 に崩壊」とは regime が違う（重みの持続的ストリーム vs 辞書の散在スカラー読み）。ESP32-S3 Errata v1.3 に該当項目は無い。
- **辞書 I/O の時間は問題にならない**（estimated）。実 NAIST-JDIC の darts を計装した実測で 1 文あたり trie 420 回 + token/feature 165 回、64 KB ページ 91 枚。全部キャッシュミスでも約 1.08 ms/文（QIO 80 MHz / 64 B ライン からの算術）で、平均発話長 3.96 s の 0.027%。
- **SD カードは mmap できない**（ESP-IDF: "mmap is supported by cache, so it can only be used on main flash"）。使うなら起動時に PSRAM へ全読み込みの一択。
- **推奨ボード: ESP32-S3-WROOM-1-N16R8**（16 MB Quad flash / 8 MB Octal PSRAM / 3.3 V）。32 MB 系は 1.8 V octal で N16R8V / N32R8V が EOL、現行 N32R16V のみと調達が脆い。
- ⚠️ **app 枠が膨らむとこの表は崩れる。** 2,048 → 4,096 KB/slot になると 16 MB / B の辞書枠は 11,456 → **7,360 KB** に落ち、辞書は約 58,500 entries / 音素列一致 約 69.7% になる。同 JSON 自身の最強の前例（esp-skainet の on-device TTS）は **4 MB の app slot** を使っている。ここは実ビルドで潰すべき最大のリスク。

## 6. 失敗例の分析

### 6-1. 未知語フォールバックは「読めない」— 誤読ではなく**無音で脱落する**

計画書 §1.5 の検証タスク 4 への答え。

`unk.dic` は 40 エントリすべて feature が 7 フィールドしかなく、**読み・発音・アクセントを一切持たない**（`名詞,一般,*,*,*,*,*` 等、全 40 件をダンプして確認）。したがって `pron="*"` のまま `njd_set_pronunciation.c:151-160` の「かなでない語は読点にする」規則に落ち、`、`（記号,読点）に置換される。音声上はポーズになり、**語が丸ごと消える。例外も警告も出ない。**

| 文字種 | 挙動 | 実例（30k 辞書） |
|---|---|---|
| 漢字（語全体が未知） | **無音で脱落** | 齟齬 → 無音 / 蜃気楼 → 蜃気(無音) + 楼(無音) / 饕餮 → 空 / 忸怩たる思い → `t a r u o m o i` |
| 漢字（1 文字ずつは既知） | 分割されて**誤読** | 氷点下 → コーリ+テン+カ / 実業家 → ミ+ギョー+カ / 所要 → トコロ+カナメ |
| かな（未知） | 仮名表で**正しく読める** | ズガピョコリン → `z u g a py o k o r i N` / ぷにゅらほ → `p u ny u r a h o` |
| ラテン文字 | 1 字ずつアルファベット読み（フル辞書と同じ） | escalator → イーエスシーエーエルエーティーオーアール |
| 全角数字 | **無音で脱落**（§6-2） | 3 → 無音 |

⚠️ フル辞書でも無音脱落は起きる（`彁という字` → `t o i u j i`、held-out で全角カンマ等 39 token instance）。**ホスト側 G2P（案4）でも消えない失敗モードなので、外字・幽霊漢字のサニタイズはどの案でも別途必要。**

### 6-2. 【最重要の欠陥】全角数字が枝刈りで落ちて数値が無音になる

全角数字 ０-９ は NAIST-JDIC の**普通の見出し語**（`名詞,数,*,*,*,*,３,サン,サン,0/2,C3`）で、pyopenjtalk は半角数字を全角に正規化してから引く。train コーパスの数字含有行が 1.86% しかないため、頻度枝刈りで簡単に落ちる。

train ランキングでの順位（measured）: ０=5,365 / １=36,003 / ７=37,897 / ５=47,348 / ６=47,925 / ８=49,985 / ４=50,703 / ２=51,135 / ３=51,141 / **９=76,948**。**９ は 60k 辞書にも入らない。**

| 入力 | フル辞書 | 30k 枝刈り |
|---|---|---|
| 午後3時15分です。 | ゴゴサンジジューゴフンデス | **ゴゴ、ジ、フンデス** |
| 1ドルは、152円35銭です。 | イチドルワ、ヒャクゴジューニエンサンジューゴセンデス | **、ドルワ、、エン、センデス** |
| 現在の時刻は、午前9時7分です。（60k） | ゲンザイノジコクワ、ゴゼンクジナナフンデス | ゲンザイノジコクワ、ゴゼン、ジナナフンデス |

**対策（measured）**: 「名詞,数」279 + 「*,接尾」2,254 + 「記号,*」202 = union **2,705 表層形**を強制追加する guard set。30k 水準で **+531,338 B** の費用に対し:

- embedded（ESP32 実運用想定 183 文）の音素列一致 **28.96% → 80.87%（+51.9pt）**
- embedded の無音化 token **194 → 27 instance**
- held-out は 67.66% → 69.72%（数字が少ないので効きが小さい）

**頻度枝刈りをするなら guard set は必須。** これが本 spike で見つかった最も実務的な知見である。

### 6-3. 失敗の種別内訳（held-out 2,325 文）

「新たに無音化した token を含む（= 読めない）」「そうでない不一致（= 間違って読む）」「音素列は一致だがアクセント句が違う」の 3 分類。

| 水準 | 読めない | 間違って読む | アクセントのみ |
|---|---:|---:|---:|
| 10,000 +guard | 33.98% | 17.94% | 13.12% |
| 30,000 full | 17.08% | 15.27% | 12.69% |
| 30,000 +guard | 13.94% | 16.34% | 13.08% |
| 60,000 +guard | 12.09% | 14.80% | 11.40% |
| 100,000 full | 8.60% | 12.43% | 10.71% |
| 200,000 full | 2.06% | 6.97% | 10.02% |

**「アクセントのみ」が 10〜13% で一定に見えるが、これは分母のせいであって床ではない。** 音素列が一致した文だけを分母に取ると 32.6%（5k）→ 26.8%（10k）→ 21.8%（20k）→ 18.8%（30k）→ 15.4%（60k）→ 13.6%（100k）→ **11.0%（200k）** と単調に 3 倍改善しており、頭打ちの兆候はない。元レポートの「アクセントは硬い床」という表現は反証済み（§7）。

**本物のアクセントの床は別のところにある**: C 実装のみの経路（Python 後処理層なし）は、フル辞書でも held-out の 23.78% でアクセント句が変わる。これは辞書サイズで縮まない。

### 6-4. アクセント型ミニマルペア（CLAUDE.md が評価セットに要求している軸）

14 文で `(pron, acc)` 列の完全一致を判定。

| 水準 | 不一致 | 内容 |
|---|---:|---|
| 10,000 +guard | 5/14 | 柿/牡蠣が両方無音化して**対立ごと消える**。飴も無音化。端・紙は後続動詞の分割が変わる |
| 30,000 +guard | 1/14 | 「舐める」が 舐め+る に分割され acc 2→0。**橋(2)/箸(1)/端(0)、雨(1)/飴(0) は保たれる** |
| 60,000 +guard | 1/14 | 同上 |
| 200,000 full | 0/14 | 完全一致 |

活用形が中途半端に落ちて分割が壊れる例（舐める → 舐め+る、寝転がっ → 寝+転がっ、役に立っ → 役+に+立っ）が全水準で多数観測された。**活用パラダイム単位で残す枝刈りに改善余地がある**（未測定）。

### 7-3. 方法論上の残る限界

- **すべて「フル NAIST-JDIC との一致」であって「正しさ」ではない。** フル辞書自身の地名・人名誤読は原理的に検出できず、ネイティブ検証済みの正解データはどこにも存在しない。**「95%」という閾値が何を保証するのかは実は不明。**
- **held-out はドメイン内。** JSUT / ROHAN / ITA / Common Voice の 90/10 層化分割（近傍重複リーク検査つき、5-gram Jaccard ≥ 0.7 の 4 行を train に戻した）。ニュース・住所・固有名詞の多い文は含まれない。唯一のドメイン外プローブは piper-plus のデモ文 41 文で、95,700 辞書が 92.68% / PER 1.06% と大幅に良く出たが n=41 では何も決まらない。
- **embedded 183 文はエージェントの手書きでネイティブレビュー未了。** 62% が数字を含むという偏った構成で、digit 欠陥が支配的に出る。1 文が 0.55% に相当する。
- **B-1 との経路不一致。** 本測定の参照は `JapanesePhonemizer` / `pyopenjtalk` 経由。教師の canonical な経路は `MultilingualPhonemizer` で、**かなを 1 文字も含まない行が丸ごと中国語音素に誤ルーティングされる**（held-out 2,325 行中 133 行 = 5.72%、embedded 183 行中 8 行 = 4.37%、大半が地名）。B-0 と B-1 で canonical 経路を揃えないと、この 5.7% で参照そのものが教師と別物になる。
- **成果物の名前が計画書と食い違っている。** 計画書の完了条件は `reports/b0_dict_footprint.json`（未知語率カラム付き）だが、実際は `b0_size.json` / `b0_coverage.json` / `b0_alternatives.json` の 3 本に分散し、未知語率カラムは無い。計画書がタスク 3 で指定する `data/splits/diverse_ja.tsv` は存在せず、自前構築のコーパスで代替した。
- **案1c（718 KB 系列）の再現スクリプトが保存されていない。** 内部算術は自己整合的だが検証手段が無い。使う前に作り直すこと。
- **案5 の 626 MMAC / 386 MB / 9.7 s は beam=1 の下限かつ算術。** 実際の config は `beam_size: 5` で MAC は約 5 倍（flash トラフィックはビーム間で重みを共有するので変わらない）。結論には 2 桁の余裕がある。
- **`scratchpad/b0/` は複数エージェントの共有ディレクトリで、実際に上書き事故が起きている。** 一次データを再利用するときはファイルの帰属を確認すること。特に `b0/compact_matrix.py` は入力 `dic.csv` を **in-place で書き換える**ので、既存の `cin_*/` に再実行すると context id が二重に remap されて辞書が黙って壊れる。

## 8. 次のアクション

### 8-1. ユーザー判断が必要（これが決まらないと 8-2 以降が決まらない）

1. **「目安 95%」は文単位か、音素（トークン）単位か。** 文単位なら判定は「入力境界の再定義」、トークン単位なら 30k / 7.13 MB でも合格し「続行」になる。B-0 の判断分岐そのものがこの一語で反転する。
2. **OTA を要件に含めるか。** 含めなければ 16 MB ボードの辞書枠は 11.19 → 13.19 MiB になる。
3. **ESP32 スタンドアロンで「任意のテキスト」を喋る必要があるか、それとも定型文＋数値スロットで足りるか。** 後者なら案4 + 案2 で完結し、辞書問題は消える。

### 8-2. 判定を確定させるために必要な残りの測定（優先度順）

1. **RAM ピークとレイテンシの spike。** ESP-IDF を入れて OpenJTalk C 本体を xtensa でビルドし、(a) app 枠の実サイズ、(b) mecab Viterbi のヒープピーク、(c) 1 文あたりの実行時間を測る。**flash だけで go/no-go を出してはいけない。**
2. **B-1 との経路統一。** 参照を `MultilingualPhonemizer` に揃え、かな無し行 5.72% の中国語誤ルーティングを塞いだうえで一致率を測り直す。B-0 の全数値はこの経路差の上に乗っている。
3. **pyopenjtalk-plus 後処理層の扱いの決着。** 教師側を `use_sudachi_kanji_yomi=False` に揃える（教師ラベル生成のやり直しが必要）か、C 実装のみの 23.78% アクセント差を許容するか。案4 を採るならこの問題は消える。

### 8-3. 枝刈り路線を続ける場合にやるべきこと（判定次第）

4. **operating point での選択規則スイープ。** 現在の曲線はフロンティアではない（§7-2）。corpus-only が 5.89 MB / 68.86% を出す一方、11.7 MB で 73.4% なので、**8 MB ボードの魅力が報告値より大きい**。活用パラダイム単位・品詞単位のランキングも試す価値がある（分割崩れが失敗の主要因のため）。
5. **guard × L2 × noread の union は誰もビルドしていない。** 16 MB ボードの実際の最適解はおそらく「約 75k 表層形 + guard + L2 + matrix 圧縮」だが未測定。
6. **数値・日付・金額のストレステスト。** guard set は 183 文でしか検証されていない。任意の大きな数・小数・日付・通貨が推奨水準で生き残るか未確認。

### 8-4. 推奨する実装方針（8-1 の 3 が「定型文で足りる」なら即着手可能）

- 蒸留の入力境界を**音素ID列**に固定する（論文 §II と同じ）。CLAUDE.md の「MCU tier の入力は音素ID列と定義する」という既存の判断は、本 spike の実測によって**強く裏付けられた**。
- ホスト側 G2P（案4）+ 定型文プリコンパイル（案2、ただし数値スロットはテンプレート込みでコンパイル）。
- 端末側の G2P 資産は 0 B〜数十 KB で済み、**辞書枝刈りは実装対象から外せる。**
- B-0 は「G2P は端末に載らないので境界の外に置く」という結論で閉じ、蒸留の実装（B-1 以降）に進む。
