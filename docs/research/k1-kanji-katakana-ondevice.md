# K-1: 端末で漢字・カタカナを扱えるか — B-0 / D-009 の否定的結論を測り直した

作成 2026-08-30 / 対象 arXiv:2608.21378 sanoTTS の日本語適用 (PoC・非配布)

前提となる先行調査: [`b0-g2p-footprint.md`](b0-g2p-footprint.md) / [`../decisions.md`](../decisions.md) D-009 〜 D-011

**このレポートの数値の扱い**

- サイズは**すべて実際にバイト列を組み立てて `len()` した値**。線形外挿は 1 つも無い（C-009 の再発防止）。
- 一致率は**「フル辞書 / 既定経路と同じ出力が出るか」であって「正しい読みか」ではない**。ネイティブ検証済みの正解データは存在しない。**聴取は一切していない。**
- 出所を 3 段階で明示する: **[自己実測]** / **[レーン報告・私が独立再現]** / **[レーン報告・未再検証]**。
- ⚠️ **WebSearch / WebFetch がこの権限モードで拒否された。** AquesTalk など**外部の先行事例は一切調べられていない**。

## 1. 結論

**カタカナは端末テーブル 0 B で入る。漢字は、辞書の持ち方を変えると B-0 が「不可能」と書いた動作点が現行ボードに載る。
そして「アクセントは C 実装では 76% で頭打ち」は誤りで、律速は語彙資源ではなく 126 行の純粋な規則だった。**

| 問い | B-0 (2026-08-26) | K-1 の実測 |
|---|---|---|
| 辞書は RAM を食うか | 未測定（§7-1 が「完全に未測定」と明記） | **mmap。98.4 MB をマップして常駐 1,040 KB** |
| フル辞書は載るか | 載らない。L2 削減でも 79,881,118 B = 76.2 MiB | **載る。25,880,002 B = 24.68 MiB** |
| 音素 95.53% / アクセント 89.29% の動作点 | 41,995,303 B = 40.05 MiB。**32 MB にも入らない** | **14,467,408 B = 13.80 MiB** |
| 16 MB / OTA2 枠 (11,730,944 B) に入る最大 | 95,700 entries → 音素 73.42% / アクセント 62.54% | **263,000 entries → 91.31% / 81.55%** |
| C 実装のみのアクセント天井 | **76.22%**（辞書では買えない床） | **床の 23.62pt は外部資源ゼロの 126 行。移植すれば 100.00%** |
| Viterbi と matrix.bin は落とせるか | 未検討 | **落とせない。ただし 3.79 MB → 1.90 MB（劣化 0.26pt）** |
| カタカナ入力のコスト | 未測定 | **テーブル 0 B**（コードポイント折り返し） |

差の出どころは 2 つだけ:

1. **B-0 が測ったのは「MeCab 形式のまま枝刈りした辞書」だった。** B-0 自身が §7-4 で
   「dedup による 17.1 MB の節約は独自バイナリ形式に進むときだけ回収できる」と書いて
   その軸を未測定のまま残している。K-1 はそこを埋めた。
2. **アクセントの床を「語彙資源の床」だと解釈していた。** 実際に効いていたのは
   pyopenjtalk-plus の後処理 7 段のうち**公開フラグを持たない 4 段**で、
   ESP32 に載らない SudachiDict / ONNX の寄与は合計 **0.13pt** しかない。

⚠️ **実機で一度も動かしていない。速度は誰も測っていない。** これはプロジェクト全体の
積年の穴（`../plan/phase0-1-implementation-plan.md` §10）そのままで、K-1 で増えたリスクではない。

## 2. TTS 専用バイナリ形式 — 何を測ったか

NAIST-JDIC の 1 エントリは MeCab 形式で約 130 B 使う（M-8 / `b0_size.json` の実測）:

```
token       16.0 B/entry   （lcAttr, rcAttr, posid, wcost, feature offset, compound）
feature   65-85 B/entry    （11 列を UTF-8 テキストで、dedup 無しで持つ）
darts     35.06 B/見出し語 （double-array trie）
```

feature が UTF-8 テキストなのが効いている。`名詞,副詞可能,*,*,*,*,今日,キョウ,キョー,1/2,C3`
を毎エントリ生で持つ。TTS が要るのはこの中の**値**であって**文字列**ではない。

### 2-1. 形式の完全性監査 **[自己実測]**

サイズを測る前に、**解析器が辞書から読むものを全部持っているか**を確かめた。
1 つでも落としていれば、B-0 の精度を新形式に貼る推論はそこで崩れる。

| 項目 | 実測 | 判定 |
|---|---|---|
| distinct (lc, rc, pos6) | **1,388** | |
| distinct (lc, rc, **posid**, pos6) | **1,388** | **posid は (lc,rc,pos6) から一意に決まる**（クラス表 +2,776 B で持てる） |
| posid が一意でない pos6 | **0 / 763** | |
| token の compound 欄 | **distinct = 1、値は 0 のみ** | 保存不要 |
| 同綴り複数エントリが token 配列上で連続 | **81,565 / 81,565 = 100.00%** | 「個数 + 開始位置」で順序ごと復元できる |

→ **形式は sys.dic の情報を 1 つも落としていない。**

### 2-2. 形式

見出し語は **LOUDS trie**（byte 単位）、値は固定長 9 B レコード + 可変長プール。
全 788,923 エントリ（`build/share` 側）での実サイズ:

| 部位 | 実サイズ |
|---|---:|
| trie: LOUDS ビット列 | 518,971 B |
| trie: ラベル (1 B/node) | 2,075,882 B |
| trie: 終端ビット | 259,486 B |
| trie: rank/select 索引 | **210,836 B**（⚠️ 訂正後。§6-1） |
| 見出し語ごとのエントリ数 | 677,700 B |
| 同 チェックポイント | 10,592 B |
| **エントリレコード (9 B 固定)** | **7,100,307 B** |
| **値プール**（pron のモーラ ID 列 / acc / orig・read の例外） | **11,465,780 B** |
| プールのオフセット チェックポイント | 12,328 B |
| mora_size 例外表 | 1,758 B |
| クラス表 / 品詞6つ組表 / 結合規則表 / モーラ表 | 49,048 B |
| **辞書本体 小計** | **22,380,930 B** |
| matrix.bin（使用 context id に詰めた。1271×1271） | 3,230,886 B |
| char.bin / unk.dic（無変更） | 268,186 B |
| **ランタイム合計** | **25,880,002 B = 24.68 MiB** |

**1 エントリ 28.29 B**（MeCab 形式の約 130 B に対して 4.6 分の 1）。

効いた点は 3 つで、どれも情報を捨てたのではなく**同じ情報の持ち方を変えただけ**:

1. **feature の値化。** 品詞 6 つ組は **763 種**、アクセント結合規則は **115 種**。
   `(lc, rc, 品詞6つ組)` の組は **1,388 種**しかないので、まとめて `u16` 1 個のクラス ID に潰せる。
2. **読みのモーラ符号化。** `pron` に出るモーラ記号は **288 種**。上位 254 種を 1 B、
   残りをエスケープ。`キョー` が 6 B の UTF-8 から 2 B になる。
3. **darts → LOUDS。** 677,700 見出し語 = **2,075,882 ノード**。
   double-array の 23,216,752 B に対し LOUDS 一式で **3,065,175 B**（7.6 分の 1）。

さらに `orig`（原形）は **63.73%** のエントリで見出し語と一致し、
`read`（読み）は **82.88%** で `pron` と一致する。フラグ 2 bit + 例外だけで持てる。

## 3. 【最重要】新形式だけを読む解析器が MeCab を完全再現した **[自己実測]**

これまでの最大の弱点は「サイズは実測だが、精度は B-0 から借りている」ことだった。
**借りるのをやめた。**

LOUDS + 9 B レコード + 値プール + matrix.bin **だけ**を読む Viterbi を書いて
`pyopenjtalk.run_mecab_detailed()` と突き合わせた:

```
=== G9 (held-out 全 2,333 文・全ソース) ===
  除外 = 182 / 2333  (MeCab が未知語と判定 78 / 私の解析器が経路なし 104)
  評価した文 n = 2151
  分割一致                2151/2151 = 100.00%
  読み一致                2151/2151 = 100.00%
  アクセント+結合規則一致       2151/2151 = 100.00%
```

⚠️ 「経路なし 104 文 (4.5%)」は**形式の欠陥ではなく私の解析器の未実装**
（char.bin / unk.dic による未知語ノード生成を書いていない）。

**[レーン報告・独立再現]** viterbi-lane も自前 Viterbi で
`pyopenjtalk` と **2,333/2,333 = 1.0000** を再現している（別実装・別コード）。

→ **B-0 の精度曲線を新形式のサイズに貼る操作が、推論から実測の裏付けに変わった。**

## 4. RAM とフラッシュ I/O

### 4-1. 辞書は mmap される **[自己実測・判定を左右した項目]**

**これが「読まれる」なら 103 MB がヒープに載り、フラッシュの議論は全部無意味になった。**
3 系統の独立な証拠がすべて一致した:

| 証拠 | 結果 |
|---|---|
| `vmmap`（陰性対照つき） | ロード前 **0 行** → ロード後 **98.4 MB のファイル由来マップ**が出現。**うち常駐 1,040 KB** |
| `nm -u` | 未定義シンボルに **`_mmap` / `_munmap`** |
| `strings` | **`N5MeCab4MmapIcEE`** = `MeCab::Mmap<char>`、`dmmap_->open(file, mode)` |
| 陰性対照 | 明示的に `read()` すると maxRSS が **98.38 MB** 動く（辞書ロードでは +2.34 MB） |

**[レーン報告・ソース読解]** ram-lane が分岐点そのものを特定した。
`open_jtalk/src/mecab/src/mmap.h:164-178`:

```cpp
#ifdef HAVE_MMAP
  CHECK_FALSE((p = (char*)(::mmap(0, length, prot, MAP_SHARED, fd, 0))) != MAP_FAILED)
  text = reinterpret_cast<T *>(p);
#else
  text = new T[length];                    // ← ヒープに 103 MB コピーする経路
  CHECK_FALSE(::read(fd, text, length) >= 0)
#endif
```

**`HAVE_MMAP` は定義されている**（推測ではなく生成済み config を読んで確認）:
`config.h:40` の `#define HAVE_MMAP 1` / `CMakeCache.txt:402` の `HAVE_MMAP:INTERNAL=1` /
`flags.make:6` で `-DHAVE_CONFIG_H` が実際に渡っている / `setup.py:138`。
さらに `dictionary.cpp:113,117,120` で **trie も token 配列も feature 文字列も
マッピング内を直接指す**（コピーしない）。

**計測器の較正（陽性対照）**: sys.dic を `open().read()` すると ΔRSS = 103,153,664 B
（sys.dic 比 **1.000**）。**103 MB のヒープコピーは確実に見える。** 見えないなら結論は無効。

**vmmap は 4 ファイルすべてを file-backed で示し、dirty = 0 K / swapped = 0 K**
（sys.dic / matrix.bin / char.bin / unk.dic）。**無名メモリは 1 バイトも使っていない。**

**Python を排した純 C++ プロセスでの常駐量**:

| 時点 | sys.dic 常駐 | matrix.bin 常駐 |
|---|---:|---:|
| 1 文だけ解析 | **160 KiB** / 98.4 MiB | 80 KiB / 3,712 KiB |
| 500 文解析 | 28.9 MiB | 3,104 KiB |

増える分は**すべて clean（dirty 0）でいつでも捨てられる**。
`pyopenjtalk` は**遅延ロード**で、`import` 直後はマッピング 0 件、
最初の `run_frontend()` で 4 件できる。

ESP32 の `esp_partition_mmap` が直接の対応物で、B-0 §5 が調べた通り
Espressif 自身のオンデバイス中国語 TTS が本番で同じことをしている。

### 4-2. ラティスは小さい **[自己実測 + レーン独立再現]**

OpenJTalk の `Mecab_analysis()` は `MECAB_NBEST` を立てない）。

**機構自体は実在する**（CLAUDE.md の「フル辞書でも起きる（外字・幽霊漢字）」は正しい）:
彁 / 妛 / 椦（幽霊漢字）、𡈽 / 𩸽（サロゲートペア漢字）、ヷヸヹ（歴史的カタカナ）は
**実際に消える**。躑躅 / 薔薇 / 顳顬 / 髑髏 / 鱲子 / 𠮟責 は正しく読まれる。
ＰＩＮ は未知語だが消えず `p i i a i e n u` と読まれる。
陰性対照（電源 / 天気 / 音声）はすべて「のこった」、陽性対照（ヷヸヹ）は「消えた」。

**[レーン報告]** viterbi-lane が `unk.dic` を実パースして機構を確認:
**未知語の feature は 7 列しかなく `read` / `pron` / `acc` / `chain` を持たない。**

## 8. カタカナ — 端末テーブル 0 B **[自己実測]**

カタカナ U+30A1..U+30F6 → ひらがな U+3041..U+3096 は
**コードポイント −0x60 の折り返し**で、凍結テーブル `csrc/g2p_table.json` の
**195 キーが 195/195 往復する**（G7）。UTF-8 バイト列のままでも
`E3 82 A1..E3 83 B6` → `E3 81 81..E3 82 96` の 2 バイト目 −1 / 3 バイト目 ±0x20 で閉じる。

折り返し規則の外にあるのは 13 文字で、**ヴ と ー 以外どれも凍結テーブルに無い**:

| 文字 | 折り返し先 | 表にあるか | 扱い |
|---|---|---|---|
| ヴ U+30F4 / ー U+30FC | ゔ / ー | **あり** | そのまま通る |
| ヰ / ヱ | ゐ / ゑ | 無し | `い` / `え` に寄せるか拒否するかの判断が要る |
| ヵ / ヶ | ゕ / ゖ | 無し | 助数詞 `ヶ月` で出る。`か` / `け` に寄せる |
| ヷヸヹヺ・ヽヾ | （変化なし） | 無し | 拒否でよい |

⚠️ **現行のホスト G2P はそもそもカタカナを出さない**（held-out 300 文で
中間表現にカタカナを含む行は 0 件）。これは
**「人が端末に直接カタカナで打てるようにする」ための機能**で、ホスト経路には影響しない。

⚠️ **入力仕様の目的を壊さないこと。** D-040 で「端末では正規化も推定もしない」と
決めている。折り返しは**規則が閉じていて往復が証明できる**変換なのでその原則に反しないが、
`ヰ→い` のような**寄せ**は推定に片足を突っ込む。
**折り返し（可逆）と寄せ（不可逆）を分けて、後者は明示的に列挙すること。**

## 9. ⚠️ 方法論上の落とし穴（後から読む人へ）

### 9-1. held-out はソース順に並んでいる

`data/splits/corpus_heldout.tsv` は**シャッフルされておらず、ソースごとの連続ブロック**:

```
行     0..  946  cv/sentence_collector      ← 先頭 947 行が単一ソース
行   947..  947  cv/singleword-benchmark
行   948..1,105  cv/yumie-text-1
行 1,106..1,147  ita/*
行 1,148..1,864  jsut/*
行 1,865..2,324  rohan4600
行 2,325..2,332  curated/question_eos
```

**「先頭 N 文」は N≤947 なら 100% 単一ソース。** K-1 の作業中に実際に踏んだ:

| | 先頭 400 | 全 2,333 |
|---|---:|---:|
| 平均文字数 | 21.1 | **26.9** |
| 最長文 | 63 | **98** |
| ラティス最大ノード数 | 474 | **659** |
| 未知語率（token） | 0.00% | **0.22%** |
| アクセント (acc,mora) 一致 | 91.25% | **81.70%** |

⚠️ **データ行は 2,333。** B-0 と M-9 が申告する 2,325 とは 8 行違う
（`data/splits/` は `.gitignore` なので差分を追えない）。

### 9-2. 辞書リビジョンが 3 つある

| 出所 | sys.dic | エントリ数 |
|---|---:|---:|
| `~/Documents/piper-plus/build/share/open_jtalk/dic` | 103,082,017 B | **788,923** |
| **`pyopenjtalk` 同梱（実行時に実際に引かれる）** | **103,131,410 B** | **789,388** |
| B-0 が申告した pyopenjtalk 側の値 | 103,094,645 B | 789,024 |

混ぜると 60 文中 43 文が「未知語を含む」と誤判定される。
**`matrix.bin` / `char.bin` / `unk.dic` は SHA-256 一致で、`sys.dic` だけが違う。**

⚠️ **[レーン報告]** ram-lane はこのマシン上に **4 種類**あることを確認している
（103,073,776 / 103,082,017 / 103,094,645 / 103,131,410 B）。
測定のたびにどれを使ったか書くこと。

### 9-3. matrix.bin の索引は MeCab 本家の式では合わない

MeCab 本家は `matrix_[lcAttr + lsize_*rcAttr]` だが、**この辞書では一致 0.91%**。
正しくは:

```
transition_cost(rc_prev, lc_cur) = flat_int16[rc_prev + 1377 * lc_cur]
```

MeCab 自身の申告値から逆算して **1,537/1,537 = 100.00%** で確定（他 3 通りの索引式はいずれも 1% 未満）。

**`link_cost` は `word_cost` を含む**（`link_cost = trans + word_cost`、`node_cost` は累積。
11/11 で確認）。これを知らずに `link_cost` と生の遷移コストを比べると、
**陰性対照そのものが壊れる**（実際に踏んだ）。

### 9-4. その他

- **LOUDS の子ノード番号は `rank1[p]`**（`rank1[p+1]` ではない）。症状が「落ちる」ではなく
  **「全部 1 文字に分割される」**なので気づきにくい。
- **位置ごとに 1 本だけ最良経路を残すのは Viterbi ではない。** 同じ位置で終わるノードでも
  rc が違えば後続コストが変わるので、**ノードごと**に最良の前任を持つ必要がある。
- **OpenJTalk は MeCab の前に半角→全角正規化を掛ける**（`?`→`？`, `T`→`Ｔ`, `~`→U+301C,
  `-`→U+2212）。94 文字の 1:1 表で、端末に載るサイズ。比較実験ではこれを両側に与えないと
  `Tシャツ` 等で不当に負ける **[レーン報告]**。
- 未知語 morph の `features` は **12 列に満たない**ことがある。ガードしないと IndexError。

## 11. 実装への含意

1. **126 行のアクセント規則を C に移植する** ← 新規性の中核。
   参照実装は `g2p_pure4.py`（scratchpad）。外部テーブルは 76 件のかな表のみ。
2. **TTS 専用バイナリ形式**（文字 ID 鍵の LOUDS + レコード + 値プール）。
   **path 圧縮は入れない**（アルファベットを詰めた後は純損）。
   値プールのオフセット チェックポイントは **32 間隔**にする。
   **orig 例外は見出し語 ID、read 例外はモーラ ID で持つ**（99.79% / 98.90% が表せる）。
   レコードは **dedup + ビットパック**（同時エントロピー 13.586 bit に対し 9 B = 72 bit）。
   **pron の dedup はしない**（ポインタ代で純損）。
3. **未知語ノード生成**（char.bin / unk.dic）。`unk.dic` の feature は 7 列。
4. **matrix.bin は int8 行ごとスケール**（3.79 MB → 1.90 MB、アクセント句 99.74%）。
   表引きが O(1) のままなので実装が最も安い。捨てるのは不可。
5. **カタカナ折り返し**（テーブル 0 B）。`ヰヱヵヶ` の寄せは明示列挙。

**ボードは 16 MB (N16R8) で 263,000 entries が現実的な最初の目標**
（音素 91.3% / アクセント 81.5%）。フル辞書を狙うなら 32 MB 系だが、
MMU の vaddr 共有（§2-4）と調達性（B-0 §5: N32R16V のみ、1.8 V octal）を先に確認すること。
