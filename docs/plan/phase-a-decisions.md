## 1. A-1: ラベル生成の入力経路

### 決定

```
漢字文 ──[ホスト・OpenJTalk]──▶ かな中間表現 ──[kana_g2p]──▶ 音素ID ──▶ 教師 ──▶ ラベル
                                                  ↑ デバイスと同じ変換器
```

**蒸留の入力は、デバイスが実際に作るものと同一でなければならない。** これが理由のすべて。

### 根拠

3 バリアントを held-out 2,325 / embedded 183 / train 20,946 の全件で比較した（measured）。

| バリアント | 表現可能率 (held-out) | 現行経路との音素ID一致 |
|---|---:|---:|
| base（mora 116） | 85.72% | 79.74% |
| ext（+外来音 41、`ん` 規則 +2） | 92.82% | 86.84% |
| **ext_norm（+ `#` のモーラ内挿入を正規化）** | **100.0%** | 93.42% |

train / embedded でも表現可能率は 100%。

### 「93% しか一致しない」を欠陥と読んではいけない

不一致の上位は**かなを 1 文字も含まない地名**だった（M-19、自己実測）。

```
埼玉県秩父市
  現行経路 (MultilingualPhonemizer) : i ɕ f u ʂ                    ← 中国語音素
  新経路   (JapanesePhonemizer)     : s a i t a m a k e N_n ch I ch i b u sh i
```

**これは B-1 そのもの。** 現行経路が壊れており、新経路が直している。
現行経路を正解とみなす前提が成り立たないので、一致率は「新経路の正しさ」の指標ではない。

### 実装に要る変更

1. `scripts/kana_g2p.py` の mora テーブルを **116 → 157 エントリ**に拡張（外来音 41）
2. `ん` の異音規則に `kw` / `gw` を追加（18 → 20）
3. `#`（アクセント句境界）がモーラ内部に現れるケースの正規化

### ⚠️ 反証で残った論点

- 「修正後、日本語として処理された行では 1 行の例外もなく一致する」は**反証済み**。例外がある
- 教師側の照合が `heldout[:200]`（Common Voice に偏る）で、**ランダムサンプルではない**
- `#` 正規化が出力を「良くする」のか「変えるだけ」なのかは未測定

## 2. A-3: ラベルパックの形式

### 決定

```
pack/
  manifest.json          生成環境・フラグ・コーパス由来・全ファイルの SHA-256
  index.npy              構造化配列。学習時に読むのはこれ
  index.jsonl            同内容 + text / source / id（人間が grep する用）
  tokens.npz             phoneme_ids / dT / prosody を連結 + offsets
  channel_stats.npz      mu_T[192] sigma_T[192] min_T[192] max_T[192] n_frames
  shards/{sid:04d}.zt.f16
  shards/{sid:04d}.yt.i16
  SHA256SUMS
```

**実装済み**: `src/saanotts_jp/labelpack.py` / テスト `scripts/test_labelpack.py`

### 根拠（すべて measured）

| 判断 | 決定 | 根拠 |
|---|---|---|
| 格納形式 | shard 化生バイナリ + memmap | npz 173 µs/utt、HDF5 114–125、圧縮 npz 792 に対し最速。部分再生成が容易 |
| `zT` | **fp16** | 実測 \|zT\| max 52.18。fp16 上限 65504 に余裕。bf16 は不可 |
| `yT` | **int16 / 固定 scale 32767** | SNR mean 76.86 dB / min 74.13 dB |
| 波形 | **持つ。STFT は事前計算しない** | log1p\|S\| は fp16 でも 12.0 B/sample で int16 の 6 倍 |
| `cT = Eρ(zT)` | パックに入れない（192ch の `zT` を入れる） | `Eρ` は 14,952 params で学習中に変わる |

### サイズ（⚠️ 訂正あり）

当初 M-15 で 4.42 GiB としたが、**先頭 60 行でベンチマークしたためサンプルが偏っていた**（C-014）。

| サンプル | `n_ids` mean | pack (fp16+int16) |
|---|---:|---:|
| 先頭 60 行 | 101.7 | 4.56 GiB |
| **無作為 400 行** | **128.3** | **5.75 GiB / 6.17 GB** |

**採用: 約 5.8 GiB。** vast.ai のディスクは 40 GB 以上を確保する。

### 健全性ゲート 13 項目

保存直前に 1 発話ごとに assert し、落ちたら採用せず `index.jsonl` に理由を残す。

特に効くのは **G7（intersperse padding の有無）** と **G12（発話速度 4–12 mora/s）**。
自前で音素→ID を組むと発話が 2.4 倍速になるが、**音声としては再生できるので他のゲートは
全部通ってしまう**（M-5）。この 2 つでしか捕まらない。

⚠️ **mora の数え方に注意。** `cl` と `N_*` は PUA (U+E005 / U+E019–E01C) なので、
トークン名の素キーで数えると**落ちる**（実測 128 文で 290 mora = 6.7% が未計上）。
`labelpack.py` は音素ID で数えるのでこの罠は踏まないが、近似（非記号 id / 2）である点は変わらない。
ゲートを 4–12 と広く取っているのはそのため。

## 3. A-2: prosody の扱い ⚠️ 反証を通っていない

> **この節の結論は検証エージェントが 6 回とも停止したため、反証を経ていない。**
> Phase B のラベル一括生成の前に、独立に確認すること。

### 暫定の決定

**ラベル生成では実 A1/A2/A3 を渡す。生徒には音素IDのみ与える**（論文の設計どおり）。

### 根拠（未反証）

調査エージェントの測定によると、コーパス 23,454 行で:

| 項目 | 値 |
|---|---:|
| ユニークな音素ID列 | 23,452 |
| 重複グループ | **2**（4 行） |
| **prosody が衝突する重複グループ** | **0** |

**同じ音素ID列に対して教師が異なる `dT` を返すケースは無い。**
したがって生徒は矛盾する教師信号を見ることがなく、決定的に学習できる。

`prosody_features` は duration predictor にしか入らず、ピッチには影響しない（M-13、確認済み）。
アクセント記号 `[` `]` `#` は音素IDとして生徒に見えるので、ピッチは学習できる。

### 確認すべきこと（Phase B の前に）

1. 上記の重複解析が **held-out を含む全件**で行われたか
2. 実 prosody / ゼロ / None の 3 通りで教師音声の品質（UTMOS）に差が出るか
3. 生徒 duration net にアクセント記号以外の入力が要るかの最終判断
