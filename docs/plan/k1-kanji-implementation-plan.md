# K-1 実装計画 — 端末で漢字・カタカナを扱う

作成 2026-08-31 / 前提調査 [`../research/k1-kanji-katakana-ondevice.md`](../research/k1-kanji-katakana-ondevice.md)

**本計画は既存の [`phase0-1-implementation-plan.md`](phase0-1-implementation-plan.md) とは別トラック**。
あちらは「かな中間表現の生徒モデル」を実機で動かす話で、残りは実機のサイクル実測だけ。
こちらは**入力境界を漢字かな交じり文まで戻す**話で、成立すればホスト G2P が不要になる。

⚠️ **本計画は「実現可能」という調査結果に乗っているが、実機で 1 度も動かしていない。**
K-1 調査の一致率はすべて「OpenJTalk と同じ出力か」であって正しさではなく、**聴取はゼロ**。

## 1. 動作点 — **実測で絞り込み済み（2026-08-31）**

計画作成時は「16 MB か 32 MB か」を未決としていたが、**3 点とも測ったので絞れた。**

### 1-1. MMU 窓 — フル辞書は現行の調達可能なボードに載らない

ESP-IDF **5.5.0** のヘッダから確定（`scripts/k1/k0_mmu_window.py`）:

| 定数 | 値 | 出所 |
|---|---|---|
| `SOC_MMU_ENTRY_NUM` | **512** | `components/soc/esp32s3/include/soc/ext_mem_defs.h:70` |
| `SOC_DRAM0_CACHE_ADDRESS_LOW/HIGH` | `0x3C000000`..`0x3E000000` = **32 MiB** | 同 `:23-24` |
| `SOC_EXTRAM_DATA_LOW/HIGH` | **同一レンジ** | `components/soc/esp32s3/include/soc/soc.h:184-185` |

**PSRAM は DBUS の窓を共有する**（`SOC_EXTRAM_DATA_*` == `SOC_DRAM0_CACHE_*`）。
B-0 §5 の主張はヘッダで裏づけられた。ボード別の flash データ用 vaddr 上限:

| ボード | PSRAM | 物理 flash | 窓 − PSRAM | 実効上限 |
|---|---:|---:|---:|---:|
| **N16R8（推奨）** | 8 MB | 16 MB | 25,165,824 | **16,777,216**（物理が律速） |
| N32R8V | 8 MB | 32 MB | **25,165,824** | 25,165,824 |
| **N32R16V（現行の 32 MB 品）** | 16 MB | 32 MB | **16,777,216** | 16,777,216 |
| PSRAM 無効 + 32 MB | 0 | 32 MB | 33,554,432 | 33,554,432 |

**結論:**

- **N16R8 では MMU は律速にならない**（窓 25.1 MB > 物理 16 MB）。効くのは
  パーティション配分だけ
- **N32R8V でも素のフル辞書 25,880,002 B は窓を 714,178 B 超える**
- **N32R16V は窓が 16 MiB に落ちる。** 最適化後のフル辞書 16,128,887 B を置くと
  残り 648,329 B で、app すら入らない → **フル辞書は不可**
- フル辞書が成立するのは **32 MB flash + PSRAM 無効**のときだけ。
  ⚠️ ただし B-0 §5 の通り **N32R8V は EOL、現行は N32R16V のみ**で調達が脆い

⚠️ **ソース読解であって実機実測ではない。** また PSRAM は全量マップされる前提で引いた。
マップ量を減らす設定があるかは未確認。

### 1-2. 16 MB ボードに実際に入るエントリ数（実測）

予算境界での内挿は禁止（C-009）なので、**実際に符号化して二分探索した**
（`scripts/k1/k0_fit_point.py`）:

| 予算 | B | **入る entries** | 見出し語 | 実サイズ | 余り |
|---|---:|---:|---:|---:|---:|
| **16 MB / B（OTA2, model 別）** | 11,730,944 | **291,952** | 234,043 | 11,409,057 | 321,887 |
| **16 MB / A（OTA 無し）** | 13,828,096 | **370,863** | 303,501 | 13,685,361 | 142,735 |
| 16 MB / C（OTA2, model 内蔵） | 10,944,512 | 276,171 | 220,205 | 10,756,762 | 187,750 |

⚠️ **精度は測っていない。** B-0 の実測点で挟むと 263,000 → 音素 91.31% /
アクセント 81.55%、400,000 → 95.53% / 89.29%。**その間**としか言えない。
**370,863 は 400,000 の 92.7% の位置**なので 95% 近傍が期待できるが、**これは期待であって実測ではない。**

⚠️ 現行の byte 単位 LOUDS での値。compress-lane の**文字 ID 鍵で trie が約 42% 縮む**ので
さらに入るはずだが、**その組み合わせはビルドしていない。**

### 1-3. ✅ 決定（D-042 / 2026-08-31）

**ESP32-S3-WROOM-1-N16R8 / OTA 無し / 370,863 entries（見出し語 303,501）。**
辞書予算 13,828,096 B に対し実サイズ 13,685,361 B、余り 142,735 B。

32 MB を選んでもフル辞書には届かず（§1-1）、調達だけ脆くなるため。
OTA を捨てたのは **+78,911 entries（+27%）**の効果が大きいから。

⚠️ **この動作点での精度は未実測。** K-3 の完了後に実測すること。

### K-1 ホスト側エンコーダ

**目的**: NAIST-JDIC → TTS 専用バイナリの変換器を、リポジトリに再現可能な形で置く。

**ゴール**: 選んだ動作点のエントリ集合が 1 本のバイナリになり、**全エントリを復元して
元の 11 フィールドと一致する**。

**受け入れ条件**（すべて陰性対照つき）:

| # | 条件 |
|---|---|
| G1 | 全エントリで 11 フィールド往復一致（調査では 788,923/788,923） |
| G2 | 陰性対照: レコードを 1 バイト壊すと G1 が落ちる |
| G3 | LOUDS の common-prefix-search が総当り参照と一致。**ヒット数を併記し、2 文字以上のヒットが十分あること**を示す |
| G4 | 陰性対照: **実際にヒットした経路上の**ラベルを壊すと G3 が落ちる |
| G5 | チェックポイントからのオフセット復元が materialise 版と一致 |

⚠️ **G3 は調査で 1 度空虚になった** — ランダム 3,000 語で組んだらヒットが 12,546 位置中
**17 件**しか出ず、「一致」の中身がほぼ全部「両方とも空を返した」だった。
⚠️ **G4 も 1 度空虚になった** — テスト文に現れないノードを壊しても不一致 0 になる。

**依拠する実測**: K-1 §2。**posid は (lc, rc, 品詞6つ組) から一意に決まる**ので保存不要、
`compound` 欄は全件 0、同綴りエントリは token 配列上 100% 連続。

### K-2 C リーダ + Viterbi

**目的**: 端末側で辞書を引き、形態素解析する。

**ゴール**: **ホストの MeCab と held-out 全数で分割・読み・アクセントが一致する。**

**受け入れ条件**:

| # | 条件 |
|---|---|
| G6 | held-out 全 2,333 文で MeCab と分割・`pron`・(acc, chain) が一致（未知語を含む文を除く） |
| G7 | 陰性対照: 接続コストを 0 にすると G6 が落ちる |
| G8 | `cc -Wall -Wextra` で警告 0、malloc をコアで呼ばない（arena を渡す。既存 C99 コアと同じ規約） |

**依拠する実測**: K-1 §3 でホスト実装が 2,151/2,151 = 100.00% を達成済み。**同じ突き合わせを C で再現する。**

⚠️ **実装で必ず踏む落とし穴**（調査で全部踏んだ。K-1 §9-3 / §9-4）:

- **matrix.bin の索引は MeCab 本家の式では合わない。** 正しくは
  `flat[rc_prev + 1377 * lc_cur]`（本家の `lcAttr + lsize*rcAttr` は一致 0.91%）
- **LOUDS の子ノード番号は `rank1[p]`**（`rank1[p+1]` ではない）。誤ると
  **落ちずに「全部 1 文字に分割される」**
- **位置ごとに 1 本だけ最良経路を残すのは Viterbi ではない。** ノードごとに前任を持つ
- `link_cost` は `word_cost` を含む。生の遷移コストと比べると**陰性対照が壊れる**

### K-3 未知語ノード生成

**目的**: 辞書に無い語で経路が途切れないようにする。

**ゴール**: **経路を張れない文が 0 件**になる。

**受け入れ条件**:

| # | 条件 |
|---|---|
| G9 | held-out 全数で経路なしが 0 件（調査のホスト実装では 104 文 = 4.5% が張れなかった） |
| G10 | 未知語を含む 78 文で MeCab と出力が一致 |
| G11 | 陽性対照: 幽霊漢字（彁 / 妛 / 椦）で**意図どおり脱落する**ことを確認 |

**依拠する実測**: 未知語は held-out 全数で **83 / 38,269 token = 0.22%**、**78 文 = 3.34%**。
中身は**ほぼカタカナの外国固有名詞の断片**（`ーヌ` `ーヴァ` `ーリャ`）と単漢字。
`unk.dic` の feature は **7 列しかなく `read` / `pron` / `acc` / `chain` を持たない**
（これが「無音で消える」の正体）。

⚠️ **未知語は誤読ではなく無音で消える。** 音では気づけないので、**脱落文字数を数えるゲート**
を必ず置くこと。

### K-5 メモリの詰め

**目的**: 1 文あたりのピーク RAM を予算内に収める。

**ゴール**: **1 文ピークが実測で 150 KB 以下**（TTS 本体 197 KB と合わせて SRAM 512 KB に
十分な余裕を残す）。

**受け入れ条件**:

| # | 条件 |
|---|---|
| G14 | 最長文でのヒープ + スタックのピークが実測されている（**スタックは調査で未計測**） |
| G15 | ラベルバッファの固定長を詰めてある |
| G16 | 陰性対照: 詰める前後で出力が bit 一致 |

**依拠する実測**: 1 文ピーク **約 251,504 B**、うち **86%（216,064 B）が
`jpcommon_label.c:668` の `calloc(MAXBUFLEN=1024)`**（実ラベルは 180 字前後）。
**1024 → 256 B にすれば約 90 KB に落ちる。**
ラティスは `mecab_node_t` 72 B（ESP32-S3 クロスコンパイル実測）× max 681、
FreeList 粒度（512 ノード単位、`free()` は返さない）込みで 73,728 B。

hook が本番パックの再生成を deny するので D-015 の扱いを決める必要がある。
