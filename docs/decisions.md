## D-001: 教師は piper-plus の `.ckpt`。ONNX は使わない

- **日付**: 2026-08-26
- **決定**: `SynthesizerTrn.infer()` を PyTorch で呼ぶ

**理由**: ONNX export は `output` と `durations` しか出さず、蒸留に必要な**潜在 `z` が
取れない**（M-7）。`infer()` は `InferOutput(audio, attn, y_mask, (z, z_p, m_p, logs_p), durations)`
を返し、これが論文の `yT` / `zT` / `dT` にそのまま対応する。

## D-003: piper-plus は HEAD (v2.0.0) をそのまま使う

- **日付**: 2026-08-26
- **決定**: `v1.13.0` への checkout も worktree も**しない**

**理由**: 当初「公開 base ckpt は FiLM 化で size mismatch する (Issue #616) ので
`v1.13.0` が必要」と考えたが、**実測したら不要だった**（M-2.4）。

- ckpt の `spk_embed_dim=192` で v2.0 の 192 次元チェックを通る
- `dec.cond.weight` が `(512,512,1)` + `cond_layers` あり = **元から post-FiLM**
- `load_state_dict` が **missing 0 / unexpected 0**、`cond_migrated=0`

むしろ `v1.13.0` に落とすと pre-FiLM 想定になって size mismatch する。

**運用**: piper-plus のリポジトリは**読み取り専用**で扱う（checkout / commit / 編集をしない）。
`sys.path.insert` で `src/python` を先頭に置く（M-1.1 の stale install 対策）。

## D-005: 音素化は `text_to_phoneme_ids_and_prosody` に `language_id_map` を渡して呼ぶ

- **日付**: 2026-08-26
- **決定**: 自前で音素→ID 変換を組まない

**理由**: `language_id_map` を渡すと multilingual に auto-promote され、
**トークン間に `_` の intersperse padding が入る**
（⚠️ 厳密には `2*n_phonemes + 3 + PAD音素数`。C-019 / M-23）。
これを飛ばすと**発話が約 2.4 倍速になる**（17.7 mora/s vs 正常な 7.6〜8.4、M-5）。

加えて自前実装は PUA 変換（M-4.2）を間違えやすく、間違えても例外が出ない。

## D-007: ターゲットは ESP32 のみ。ブラウザは対象外

- **日付**: 2026-08-26（ユーザー判断）
- **決定**: 567 K embedded tier が唯一の成果物。1.4 M は検証用の足場

**理由**: **ブラウザは piper-plus の WebAssembly で既に解決済み**なので、そこを
再実装しても価値がない。「ESP32 に対応できなければ意味がない」。

**この決定が計画に与えた影響**:

| 項目 | 変更前 | 変更後 |
|---|---|---|
| 成果物 | 1.4 M quality (browser) を優先 | **567 K embedded (ESP32)** |
| 1.4 M の位置づけ | 本命 | **足場**（レシピが日本語で効くかの確認と、567 K との差分測定） |
| オンデバイス G2P | 「音素ID入力に割り切る」で回避 | **回避不可。成立しなければプロジェクトが無意味** |
| 最優先タスク | ラベル生成の疎通 | **B-0（G2P フットプリント spike）** |

**根拠となる観測**: 辞書 102 MB のうち **65.2% が feature 文字列**で、TTS には不要な
品詞・活用情報が大半（M-8）。枝刈り + feature 削減で数 MB に収まる可能性があり、
「102 MB だから不可能」という初期判断は雑すぎた。ただし線形概算なので B-0 で実測が必要。

**判断分岐**: B-0 で「数 MB で実文の 95%+ が正しく読める」が示せなければ、
入力境界の再定義（かな入力限定 / 定型文プリコンパイル / ホスト側 G2P）か
プロジェクト自体の見直しになる。

**2026-09-03 追記（[D-050](#d-050)）**: **この決定は生きている。**
ブラウザで動くデモ（GitHub Pages）を配ることにしたが、**成果物は今も 567 K の embedded tier**で、
Web は**触れる入口**でしかない。⚠️ **「ブラウザ向けに作り直す」ことは今も対象外**
（[requirements.md](requirements.md) §2.2 の非目標のまま）。
動いているのは **`csrc/` の C99 コアそのもの**で、arena も ESP32 と同じ 180,224 B。
経緯と制約は [D-050](#d-050)、実測は [M-94](measurements.md#m-94)。

## D-009: B-0 の結論 — G2P は端末に載せず、入力境界を音素ID列に置く

- **日付**: 2026-08-26
- **状態**: **測定完了。ユーザー判断待ちの論点が 3 つ残る**
- **一次データ**: [`research/b0-g2p-footprint.md`](research/b0-g2p-footprint.md),
  `reports/b0_{size,coverage,alternatives,flash_budget,feature_fields}.json`

### 測定結果（すべて実ビルド + held-out 2,325 文）

| 問い | 答え |
|---|---|
| 16 MB ボード + OTA 2 枠 (11.73 MB) に収まる最大辞書 | **60k表層 +guard+noread = 11.57 MB** |
| その一致率 | **文単位 73.0%** / トークン単位 PER 2.36% (= **97.6%**) |
| 文単位 95% に必要な辞書 | **400k entries = 40.05 MiB** → **32 MB ボードにも入らない** |
| アクセント込み 95% | **400k / 40 MiB でも 89.29%。届かない** |

### さらに根本的な制約（辞書サイズと無関係）

教師の G2P (`pyopenjtalk.extract_fullcontext`) は **pyopenjtalk-plus の Python 後処理層**
（SudachiDict 207 MB + nani ONNX）を**デフォルトで通る**。これは ESP32 に載らない。
C 実装のみ (`use_vanilla=True`) に落とすと、**フル 103 MB 辞書でも**:

- 音素列 **95.4%**（自己実測 800 文。うち無声化のみの差が 1.88% なので、それを許容すれば 97.25%）
- アクセント **76.2%**（レポート、アクセント句単位）/ **84.0%**（自己実測、A1 単位）
  ⚠️ **どちらも C-045 で条件が判明した。** 76.22% は piper-plus 側の辞書でのみ再現し、
  **その辞書を教師は使っていない**（同梱辞書なら 79.98%）。さらに
  **この床は語彙資源ではなく 126 行の純関数**で、語彙 2 段だけ切れば **100.00% 一致**する。

**これは辞書を大きくしても縮まない下限。** ただし M-11 の通り、
**ラベル生成側も `use_vanilla=True` に揃えれば原理的に消える**（要検証）。

### 決定

**蒸留の入力境界を音素ID列に固定する**（論文 §II の "external G2P excluded" と同じ境界）。
CLAUDE.md の既存の判断が本 spike の実測で裏付けられた形。

- ホスト側 G2P: 端末フットプリント **0 B**、精度は教師と同一、回線 **68 B/文**
  （音声を Opus で流すより 2 桁小さいので「端末で合成する」利点は失われない）
- 完全スタンドアロン用途は**定型文プリコンパイル**: 1 B/音素、通知系 **40.4 B/文**、
  1,000 文で 40 KB。同じ文を PCM で焼くより 3,228 倍小さい
- **辞書枝刈りは実装対象から外す**

### 実務的に最も価値のある発見: guard set

頻度枝刈りをすると**全角数字が落ちて数値が無音で消える**。
`午後3時15分です。` → `ゴゴ、ジ、フンデス`（`９` は 60k 辞書にも入らない）。

未知語は**誤読ではなく無音で脱落する**（`unk.dic` の 40 エントリは読み・アクセントを
一切持たないため `、` に置換される）。例外も警告も出ない。

対策は「名詞,数」279 + 「*,接尾」2,254 + 「記号,*」202 = **2,705 表層形の強制追加**。
30k 水準で +531 KB の費用に対し、embedded セットの音素列一致が
**28.96% → 80.87%（+51.9pt）**、無音化 token が 194 → 27 instance。

**枝刈り路線を採らなくても、この「未知語は無音で消える」性質は
入力サニタイズの設計に効く**（外字・幽霊漢字はホスト側 G2P でも同じ失敗をする）。

### ⚠️ ユーザー判断が必要な 3 点

1. **「目安 95%」は文単位かトークン単位か。** 文単位なら「入力境界の再定義」、
   トークン単位なら 30k / 7.13 MB でも合格し「枝刈り続行」もあり得る。**判定が反転する**
2. **OTA を要件に含めるか。** 含めなければ 16 MB ボードの辞書枠は 11.19 → 13.19 MiB
3. **任意テキストを喋る必要があるか、定型文＋数値スロットで足りるか。**
   後者なら辞書問題は消える

### ⚠️ go/no-go を出す前に必要な残測定

- **RAM ピークとレイテンシが完全に未測定。** flash に入っても OOM すれば落ちる。
  ESP-IDF がこのマシンに無く、xtensa ビルドもしていない
- **B-1 との経路不一致**: B-0 は `JapanesePhonemizer`/`pyopenjtalk` 基準だが、
  教師の canonical 経路は `MultilingualPhonemizer`。かな無し行 5.72% が中国語に誤ルーティング
  される問題の上に全数値が乗っている

## D-010: ひらがな入力仕様 — 読みは 1.6 KB で解決、アクセントは入力に持たせる

- **日付**: 2026-08-26（ユーザー提案）
- **状態**: 測定完了。**D-009 の結論を部分的に覆す good news**
- **一次データ**: [`measurements.md`](measurements.md) M-12

### 提案

「漢字・カタカナを除外し、**ひらがなのみ入力**を受け付ける仕様に変更する」

### 測定結果

**読みは解決する。** かな→音素は決定的な規則で、**mora テーブル 1,644 B**。
無声化を正規化した PER は **0.272%**。40 MB の辞書が 1.6 KB の表になる。

**アクセントは解決しない。しかも辞書を積んでも直らない**（自己実測 500 文）:

```
漢字かな交じり → ひらがな化 → フル 103MB 辞書で再解析
  音素列    一致 84.00%
  アクセント 一致 15.00%   ← 辞書サイズと無関係
```

原因は分割の曖昧性であってサイズではない。かなにすると語境界と語義が失われるので
Viterbi でも復元できない。**かなキーのアクセント辞書を積んでも上限は同じ 15%。**

### 決定

**アクセント記号を入力に含める。** `[`（上昇）/ `]`（下降核）/ `#`（句境界）は
**すでに音素列のトークン**なので、入力がこれを持てば端末側の推論が不要になる。

| 案 | 端末フットプリント | アクセント精度 |
|---|---:|---|
| **ひらがな + アクセント記号** ← 採用 | **~2 KB** | **教師と同一** |
| ひらがなのみ + かなアクセント辞書 | 0.16〜15 MB | 15%（上限） |
| ひらがなのみ・平板 | ~2 KB | 平板（棒読み） |

### D-009 との関係

D-009 は「辞書路線は成立しない → 入力境界を音素ID列に置く」だった。
D-010 はその**中間点**を作る:

- 音素ID列（D-009）: 端末 0 B、完全、だが人間が読めない
- **ひらがな + アクセント記号（D-010）: 端末 ~2 KB、完全、かつ人間が読み書きできる**
- 漢字かな交じり: 40 MB でも 73%

**ファームウェアに `でんき]をつけま]す` のような読める文字列を置ける**ことの
保守性の利益は大きい。定型文プリコンパイル（音素ID焼き込み）より扱いやすい。

### ⚠️ 未検証

- ひらがな + アクセント記号から音素ID列を組む実装を書いて、
  漢字版と bit 一致することを確認していない（M-12 は既存経路での測定）
- アクセント記号を人手で付けるコスト。**ホスト側で漢字→かな+記号に変換すれば自動化できる**
  （変換はオフラインで一度やればよい）
- 平板読みが実用に耐えるかの聴取評価
- カタカナ語をひらがなで書く際の表記ゆれ（`コンピューター` → `こんぴゅーたー`）

<a id="d-011"></a>
## D-011: 入力仕様を確定 — ひらがな + アクセント記号 + 無声化マーク

- **日付**: 2026-08-26（ユーザー決定）
- **状態**: **確定。要件定義書 [`requirements.md`](requirements.md) に反映済み**

### 決定

本プロジェクトの入力は **中間表現「ひらがな + アクセント記号 `[` `]` `#` + 無声化マーク `°`」**とする。
漢字かな交じり文は端末で扱わない。

### 根拠（すべて実測）

| 方式 | 往復一致率 | 端末フットプリント |
|---|---:|---:|
| ひらがなのみ（フル 103 MB 辞書でアクセント推定） | 15.0% | 103 MB |
| ひらがな + アクセント記号（無声化は規則） | 59.6% | 951 B |
| **ひらがな + アクセント記号 + 無声化マーク** | **100.0%** | **951 B** |

無声化を規則で推定すると **170 箇所を過剰無声化**した。品詞とアクセント型に依存するため
規則化できない。→ **入力に持たせる**。

### これで解決したこと

- 辞書 40 MB → **951 B**。8 MB フラッシュのボードでも余裕
- アクセント精度が教師と同一（記号は音素IDそのもの）
- **ファームウェアに人間が読み書きできる文字列を置ける**（音素IDのバイト列より保守しやすい）

### 副次的な確認: アーキテクチャの変更は不要

アクセント記号は音素ID 8 / 9 / 7 で、英語の強勢記号 `ˈ`(87) `ˌ`(88) と同じ機構。
VITS はピッチを潜在 z に持ち、z は音素IDから決まる。記号位置を1つ変えると
F0 が **42.8 Hz** 変わることを実測（M-13）。**生徒に韻律入力を足す必要はない。**

なお `prosody_features` (A1/A2/A3) は duration predictor にしか入らず、
ピッチには影響しない。論文の生徒設計（acoustic は音素IDと duration のみ）は日本語でも正しい。

```bash

```

## D-013: 品質は「教師比」と「人間音声比」の両方で報告する

教師の UTMOS が 1.748 と出た。論文の教師 4.42 と比べると壊滅的に見えるが、
**実人間の日本語音声（教師の元コーパス）を測ったら 2.305 しかなかった。**

同一エンジンで言語だけ変えた piper-plus のデモ音声でも

## D-016: デプロイ語彙は 57。浮いた 8,000 params は width に回さない

**日本語のデプロイ語彙は 57 トークン**（論文の英語版は 157）。
`kana_g2p` の mora テーブル + `ん` の異音規則 + 無声化 + 長音 + 記号から
**原理的に出せる音素の閉包**であって、コーパス出現 51 の上位集合（M-26）。
コーパスに出ただけの語彙で凍結すると、実運用で未出現の音素が来た瞬間に壊れる。

`VOCAB` 157 → 57 で **567,008 → 559,008 params**（−8,000, −1.41%）。

**浮いた 8,000 params は width に回さない。** 理由:

1. **語彙削減で MMAC は 1 も減らない**（埋め込みは表引きで 0 MAC）。浮いたのは
   flash 8 KB だけで、flash は逼迫していない
2. width に回すと **MMAC は増える方向にしかならない**（+0.20〜+0.53 MMAC/s）。
   ESP32 で逼迫するのは flash ではなく実時間
3. 8,000 params は総量の 1.41%。品質への寄与は測れないほど小さいと見込まれる

⚠️ **生徒は教師の音素ID をそのまま埋め込みに使えない。** 57 トークンの教師 ID は
最大 64 で 8 個の穴がある。`src/saanotts_jp/vocab.py` の `TEACHER_TO_STUDENT` を
必ず通す。**この写像表は重みと一緒に凍結する。**

⚠️ **当初 6 トークンのコーパス出現が 0 だった。3 つは解消済み。**
- `?!` `?.` `?~` は**ホスト G2P が原文の約物から出す**ので到達可能なのに、
  コーパスに 1 行も無かった。**疑問 EOS 4 種を含む実文 47 行を足した**
  （`scripts/b9_add_question_eos.py`、train 39 / heldout 8）。使用音素 51 → 54。
  併せて `〜`(U+301C) が `?~` にならず**約物が黙って消える**問題を
  `kana_g2p.normalize_input()` で塞いだ
- **`A` `E` `O` は残る。** 無声化母音だが日本語の母音無声化は狭母音 `i` `u` に
  ほぼ限られるので実データに出ない（C-004）。未学習行を残さないよう
  `a` `e` `o` と**同値初期化**する

## D-018: `_` PAD は他のトークンと同じ扱いにする（D2 の決着）

## D-019: `s_v = 1.2187` を初期値にする（量子化ぶんのみ。学習後に解き直す）

教師は `w_ceil = ceil(w)` でフレームを割り当て、生徒は

コーパス全体で総フレームを一致させると **`s_v = 1.2187`**、発話ごとの比は
mean 0.9984 / sd 0.0206 に収まる（`s_v=1.0` では 0.8135）。

⚠️ `r_i` に生徒の予測ではなく `dT` を代入している（完璧な生徒の仮定）。
**学習後に生徒の予測で解き直す。**

**`clip_[1,80]` について**: 上限 80 は飽和しない（max ceil 30）。

## D-021: λ は勾配整合で初期化し、`λ_n` / `λ₂` は実行時に計算する

`L_c` の内訳は "the weighted sum implemented by the trainer" としか書かれていない。

| `λ₂` | — | **実行時**に残差 RMS から `1/(2·RMS)`。結果として L2 が RMS 項になる |
| `λ_Δ` | **0.86** | 定数（探索対象） |
| `λ_s` | **0.19** | 定数（探索対象） |

（初期化時 0.397 → 収束するほど上昇）。「2.0 から減衰」は方向が逆。

**式2 のターゲットも直した**。`r = max(1, exp(l̂))` に clamp があるのに

length 項が 0 にならず、発話を 4.4% 短くする定常バイアス**になる（C-021）。
`Σ max(1, dT)` にして自己整合させた。

**残る探索対象は `λ_Δ` / `λ_s` / `λ_T` の 3 つ**（`λ_n` `λ₂` は閉形式で不要）。

## D-029: Phase D-2 はステート保持型ストリーミングにする（chunk=8）

### 目的

**C99 コアを ESP32-S3 の SRAM に載せる。** これが Phase D-2 の唯一の目的。
品質は既に目標へ届いており（M-37）、残る障害はメモリとレイテンシだけ。

現状は**発話全体をバッファ**していて **1.26 MB = SRAM 512 KB の 246%**（M-41）。

### ゴール（受け入れ条件）

| # | 条件 | 測り方 |
|---|---|---|
| **G1** | **ピーク RAM < 200 KB** | arena の高水位を実測する。ヒープではなく arena で測る |
| **G2** | **一括版と bit 完全一致** | 同じ入力で `memcmp`。⚠️ 「SNR が高い」では**不可**。チャンク境界の取りこぼしは SNR に埋もれる |
| **G3** | 発話長に対して RAM が **O(1)** | 10 / 100 / 1000 フレームで arena 高水位が変わらないこと |
| **G4** | golden test が通り続ける | 既存の `make test` |

**G2 を bit 一致にする理由**: チャンク境界で 1 フレーム落としても、
27,136 サンプル中の 256 サンプルなので SNR は 20 dB 出てしまう。**閾値では捕まらない。**

### 受容野（実測。⚠️ 計画書の旧記述は誤りだった）

| 経路 | 実測 | 理論 | 旧記述 |
|---|---:|---:|---:|
| decoder | **±16** | inp k=3 (±1) + dw k=7 × 5 (±15) | ±16 ✅ |
| acoustic frame | **±20** | (c1 k=5 + c2 k=5) × 5 段 | ~~±10~~ ❌ |

**旧記述の ±10 は `c1` だけ数えていた。** `AcBlock` は c1 と c2 の 2 つを持つ。
実測は「1 フレームだけ変えて出力の何フレームが動くか」で取った
（⚠️ **閾値 1e-6 だと decoder が ±13 に見える**。端の寄与が小さいだけなので閾値 0 で測る）。

### 方式の比較（実測に基づく）

| 方式 | ピーク | 計算量 | 判定 |
|---|---:|---:|---|
| (A) 一括（現状） | 1,258 KB | 1.0x | ❌ 載らない |
| (B) ハロー再計算 chunk=8 | 192 KB | **10.0x** | ❌ 計算が 10 倍 |
| (B) ハロー再計算 chunk=32 | 404 KB | 3.2x | ❌ 載らない |
| **(C) ステート保持 chunk=8** | **97 KB** | **1.0x** | ✅ **採用** |
| (C) ステート保持 chunk=1 | 36 KB | 1.0x | メモリ最小だが呼び出し回数が 8 倍 |

**(C) を採る。** 各 conv 層が左コンテキスト `(k-1)` フレームを保持し、
チャンク間で繋ぐ。**ハローの再計算がゼロ**になる。

⚠️ **代償はレイテンシ**。出力は受容野ぶん **36 フレーム = 0.42 秒**遅れる。
ESP32 の目標 0.22× RT に対しては許容範囲だが、**対話用途では効く**ので記録しておく。

⚠️ **chunk=8 は「メモリと呼び出し回数の折衷」であって最適化していない。**
実機で測ってから調整する余地がある。

### やらないこと

- **int8 カーネル**は Phase D-3。ここでは fp32 のまま構造だけ変える
  （2 つ同時に変えると、どちらが原因で bit 一致が崩れたか分からなくなる）
- **FFT 化**も分ける。naive DFT のままで G1〜G4 を通し、そのあと差し替える

## D-030: アクセント型の評価は「固定キャリア文中のペア内コントラストの向き」で測る

### 何を決めたか

CLAUDE.md の未解決 #5「アクセント型の再現性」を数字にする方法を凍結した。
設定は `src/saanotts_jp/accent.py`、評価セットは `data/splits/accent_pairs.tsv`、
実行は `scripts/d4_accent_pairs.py`、結果は **M-44**。

| 決めたこと | 値 | 理由 |
|---|---|---|
| 主指標 | `cos(Δ_T, Δ_S)` の**符号**と平均 | 下記「差の有無は証拠にならない」 |
| キャリア | `そこに{}がならんでいる。` / `ここに{}があるよ。` | **語を文中に置く**。下記 |
| 教師ゲート | `\|Δ_T\| >= 1.5` semitone | 教師が弁別しないペアで生徒を減点しない |
| F0 | `librosa.pyin(fmin=150, fmax=600, frame_length=1024, hop_length=256)` | hop が教師フレームと一致 |
| モーラ区間 | 音素 + **各音素の直後の PAD**、記号 `[ ] #` は除外 | PAD がフレームの過半を占める |
| 統計 | **グループ単位**のクラスタ bootstrap | 同一群の 2 キャリア × 最大 3 メンバーは独立でない |
| 落とした指標 | ピーク位置（argmax モーラ） | 実測 0.391 で chance 相当（M-44） |

### 「A と B の音が違う」を証拠にしてはいけない

群内のメンバーは**記号を除いた音素列が完全に同一**なので、出力の差はすべて
アクセント記号に起因する。したがって「生徒が記号を使っているか」は**問いにならない**
（必ず使う）。しかも `[` `]` `#` は教師で実フレームを持つので、
**アクセントを完全に無視するモデルでも A と B は違う音になる**。

問うべきは **「教師と同じ向きに使っているか」** だけ。だから差の大きさではなく
`cos` の符号を主指標にした。

### chance は 0.5 ではない

全ペアが同じ 2 本のキャリアを共有するので `Δ` どうしに相関が残る。
順列ヌルの実測は **cos>0 が 0.614 / cos 平均 +0.135**（M-44）。
**0.5 を分母にすると有意性を過大評価する。** 経験的ヌルを併記すること。

### 語を文頭に置くと指標が壊れる（設計を変えた理由）

最初に試した `{}が好きです。` / `{}を見ました。` は 2 つの理由で使えなかった:

1. 文頭モーラの F0 が取れず（橋/端 の `は` が欠測）、`]` 境界の下降 AUC が
   **教師自身で 0.4624**（下降ではなく上昇として出る）。文中配置で 0.7049 に回復
2. `す°` `し°` を含むため無声化モーラで F0 が原理的に取れず、
   群内の共通有声モーラが 0〜2 まで落ちて hashi / kaki が群ごと評価不能になった

**キャリアを変えたら必ず教師ベースラインを取り直すこと。**

### 語を決める手順（記憶で書かない）

アクセント型は **`pyopenjtalk.run_frontend(word)[0]["acc"]` から取り、
スクリプトが assert する**。実際に当たったところ、思い込みで挙げた候補の多くが
不成立だった:

| 落とした候補 | 理由 |
|---|---|

## D-031: 重みは flash の `model` パーティションに置き、arena は実測から 208 KB を静的確保する

### 何を決めたか

ESP32-S3 の雛形（`esp32/`、M-46）で、**重み blob の置き方**と
**arena の大きさの決め方**を凍結した。

| 項目 | 決定 |
|---|---|
| 重みの置き場所 | flash の `model` パーティション。`esp_partition_mmap()` で読む |
| **`EMBED_FILES`** | **使わない**（アライメント無保証） |
| パーティション表 | カスタム（`esp32/partitions.csv`）。`model` の offset は **64 KB 境界** |
| arena | `.bss` に **208 KB (212,992 B)** を静的確保 |
| arena の根拠 | **実測**（`make -C csrc arena`）。`saan_stream_arena_needed()` は**使わない** |
| 既定の blob | fp32 `student.bin`。int8 は `-DSAAN_MODEL_BLOB=...` で切り替え |

### なぜ

**1. SRAM にコピーしない。** blob は 643,936 B（int8）〜 2,249,792 B（fp32）で、
512 KB の内部 SRAM に入らない。コアは blob を書き換えないので read-only の
mmap で足りる。

**2. `EMBED_FILES` はアライメントを保証しない。**
`idf_component_register(EMBED_FILES ...)` は `target_add_binary_data()` を
**ALIGN 引数なしで**呼び、`data_file_embed_asm.cmake` は `DATA_ALIGNMENT` が
未定義なら `.balign` を出さない。本コアは payload を `const float*` に直接
キャストし（テンソル offset は全部 16 の倍数 — M-46 (f)）、Xtensa は
非アラインの 4 バイトロードで `LoadStoreAlignmentCause` になる。
しかも**リンク結果次第でたまたま揃うことがあり、無関係な変更で突然落ちる**。

⚠️ この `EMBED_FILES` の挙動と、`esp_partition_mmap()` が 64 KB 境界に
丸めるという挙動は、**ESP-IDF の公式 cmake / ソースを読んで得た事実であって、
この環境には IDF が無いので再確認していない**。だから
`esp32/main/saan_model.c` は挙動を信用せず、**実行時に 16 バイト境界を検査して
落とす**。

**3. `saan_stream_arena_needed()` を静的確保に使ってはいけない。**
n_ids=350 に対し **340,016 B (332 KB)** を返す緩い上限で、512 KB の 65% を占める。

**4. M-42 の「197 KB」も確保量ではない。** あれは高水位（`st.peak_used`）で、
**init が通る最小 arena は 197,632 B**（M-46 (b)）。

208 KB の根拠は実測（M-46 (b)）: 最小 197,632 B に対し 15,360 B の余裕があり、
n_ids 520 まで伸び、560 以上は `SAAN_ERR_ARENA` できれいに失敗し、
n_ids 1〜1000 の 23 点でクラッシュ 0。設計上限は 350 ids
（D-017 の `max_spec_length=700` 相当）。

### 一緒に決めたこと

- **タスクスタックは 16 KB を明示**する。`saan_irfft_1024` の自動変数だけで
  4,096 B（M-46 (e)）。合成は `app_main` ではなく専用タスクで回し、
  チャンクバッファと int16 変換バッファは `static` にしてスタックから外す
- **`i2s_channel_enable()` の前にプリロール**する。初回 pull は定常の 6.0 倍
  （M-46 (d)）
- **`-std=c99` を component に足さない**。IDF 既定の gnu17 のまま
  （newlib の `M_PI` が `__STRICT_ANSI__` で隠れうる。手元では再現しない）
- **`SAAN_FFT_DOUBLE` / `SAAN_USE_NAIVE_DFT` は定義しない**（S3 は単精度 FPU のみ）
- **コアは `csrc/` を相対パスで直接参照**する。コピーもリンクもしない。
  ⚠️ **4 ファイルすべて**（`saanotts_int8.c` を含む）— M-46 (a)

### ⚠️ その後に変わった値（2026-09-03 追記）

**上の表は 2026-08-29 時点の凍結値である。実装は 2 箇所がその後動いた。**
CLAUDE.md は「設計値は D-016 〜 D-048 として凍結」と案内するので、

## D-032: 公式実装 (GPL-3.0) は**ドキュメントだけ参照し、ソースコードは読まない**

### 何を決めたか

公式実装 [`Ampixa/sanoTTS`](https://github.com/Ampixa/sanoTTS) が実在すると判明した（C-024）。
**本リポジトリは MIT で既に公開済み**なので、次の線を引く。

| 行為 | 可否 | 理由 |
|---|---|---|
| 公開ドキュメント（README / `docs/*.md`）の**数値・ハイパーパラメータ・構成**を参照 | ✅ | **事実は著作権の対象外** |
| リポジトリのメタデータ・ファイル名一覧の照会 | ✅ | 同上 |
| ソースコード（`.c` / `.py` / `.S` …）の取得・コピー | ❌ | **GPL-3.0 が伝播し MIT のまま配布できなくなる** |
| ソースを読んでから書き直す | ❌ | グレー。**特にアセンブリは表現の幅が狭い** |
| `uv add sanotts` | ❌ | `.venv` に GPL のコードが入る |

### なぜこの決め方か

**うちが上流から本当に欲しいのは PIE アセンブリ（3.4 KB）と ESP-IDF ポートの 2 つだけ**で、
それ以外はレシピの数値で足りる。そして**その数値はもう取れた**
（[`upstream-sanotts.md`](upstream-sanotts.md)）。

**アセンブリ 3.4 KB のために MIT を捨てるのは割に合わない**という判断。

⚠️ **方針を変えて GPL-3.0 に再ライセンスするなら、この決定ごと撤回すること。**
その場合は hook の `check_upstream_gpl` / `check_upstream_package` も外す。

### どう強制するか

`.claude/hooks/guard_bash.py` が Bash 実行前に deny する（回帰 94 ケース）。
**ドキュメント取得は通す**ので、事実の参照は今までどおりできる。

⚠️ **作った直後に誤検知を踏んだ**（`grep -rn "Ampixa/sanoTTS" --include="*.py" .` が
deny された）。拡張子をコマンド全体から探していたのが原因で、
C-011 / C-015 / C-020 / C-025 と**同じ病理**。
**上流を指すトークンの中だけ**を見るよう直し、自リポ検索 3 ケースを回帰に固定した。

### 記録の扱い

上流由来の数値は **`docs/upstream-sanotts.md` に隔離**し、全項目「上流申告値・未再現」と明示する。
**`docs/measurements.md` の M-番号（自己実測）と混ぜない** —
混ぜると「ESP32 で 0.22× RT が出た」と読める記述ができあがる（実機は一度も動かしていない）。

  と書かれており、**`cmd`（コマンド文字列全体）**から `-i` を探していた。
  **1 行目の `perl -i` が `-[a-zA-Z]*i` に一致**するので免除が外れ、
  3 行目の読み取り `sed -n` が piper-plus パスとして deny された。

- **これが 3 度目である理由**: 病理は毎回同じで
  **「1 コマンドに閉じるべき走査を、ブロック全体に広げている」**。
  - C-015: `CMD_POS` が改行を跨いでいた
  - C-020: C-015 で直したはずの改行の扱いが**別の関数に残っていた**
  - C-025: 引数側の走査は `[^;&|\n]` で閉じてあったのに、
    **その隣の `-i` 判定だけが `cmd` 全体を見ていた**

  すぐ下のコメントが「引数の走査に `\n` を含めない」と警告しているのに、
  **同じ 4 行の中で別の走査が全体を見ていた。**

- **対応**: `re.finditer` で **`sed` の呼び出しごとに区切った文字列**を取り出し、
  `-i` はその中だけを見るようにした。回帰テストを **60 → 63 ケース**に拡張
  （別行の `perl -i` / 同一行の別 `sed -i` / 本物の `sed -i` が改行を跨ぐ場合）。

- **教訓（誤検知はこれで 5 回目）**: **区切り文字の定義を 2 か所に散らさない**という
  従来の教訓では足りなかった。**「このコマンドの引数」を見る判定は、
  必ず先にコマンド単位へ切り出してから行う。**

## C-026: 「金属的な尾が出たら E-2 の仮説 (a) の証拠になる」→ 誤った推論

## C-027: 「blob2 の制約を満たす構成が 0 件 → 論文の `Gγ` 逆算が最有力に間違い」→ 前提が違う

`reports/r3_blob2_constraint.py` は

```
blob = P + 3B + 4C          （W_int8 + 4*B_fp32 + 4*C_scale, W + B = P）
```

を制約に `3B + 4C == 68,236` を満たす構成を探し、**0 件**という結果から
「論文の逆算が間違っている」と読める報告になっていた。

**論文本文（自分で取得。sha256 `64b0d426…`）§III-A はこう書いている**:

> **Padding**, floating-point biases, and per-channel scales account for the
> difference between parameter count and binary size.

**`blob = P + 3B + 4C` には padding 項が無い。** さらに §V は

> Embeddings, normalization affines, and **the inverse-STFT support code**
> remain in floating point.

と書いており、**iSTFT 支援表（窓 / twiddle / bit-reversal）も未計上**だった。
したがって「0 件」は「解が無い」ではなく「**前提が違う**」を意味する。

**対応**: padding（テンソルごとのアラインメント A ∈ {4,16,64} B、上限は
テンソル数 ×(A−1) で計算できる）と iSTFT 支援表（最大 16,384 B）を
**探索前に宣言して**測り直した（`reports/e2_blob_padding.py` / M-49 結果 F）。
結果は **合計 679,832 B は align-64 の宣言なら到達可能**（必要 23,140 / 余地 27,913）、
align-16 と align-4 では不可能。**論文は blob の中身を書いていない**ので
per-blob の食い違いは `Gγ` の証拠にならない。

→ **(a1) は blob 算術では決着しない。** 「0 件だから (a) が最有力」とは書けない。

⚠️ **padding を自由変数にしてはいけない。** 上限を宣言しないと 38,680 B の不足は
どんな構成でも埋まり、**(a) を好きな向きに「否定」できてしまう**。
`reports/e2_blob_padding.py` は陽性対照（同じ規則で再計算して 360,864 B に一致）と
陰性対照（`dw` を 1 本抜くと 360,028 B に変わる）を持つ。

**教訓**: **一次ソースが「差分の内訳」を列挙しているなら、その全項目をモデルに入れてから
「解が無い」と言う。** 項目を落としたモデルの「0 件」は、相手ではなく自分の否定である。

⚠️ ただし **SIG だけはフレームレート 86.13 Hz の AM に選択的**（雑音より厳しい）。
「金属的」がフレーム境界の周期性を指すなら**見るべきは OVRL ではなく SIG**。
⚠️ **これは代理に対する感度であって、うちの生徒に実在する欠陥に対する感度ではない。**
⚠️ 上流の申告値は `docs/upstream-sanotts.md` に隔離したままにする（**未再現**）。

**リポジトリの `LICENSE`（MIT）を重みに適用してはいけない。**

MIT は "without restriction" の利用を認める。しかし重みは
つくよみちゃんコーパスを素材に含む教師からの蒸留物で、そのコーパスの条件は

2. **出力の用途に禁止事項**を課す（個人攻撃 / 政治・宗教 / アダルト / 素材再配布）

<a id="d-040"></a>
## D-040: 端末の自由入力は「かな中間表現の 1 行」で受ける。**正規化も推定もしない**

**決定（2026-08-30）。** シリアルから 1 行受け取って合成する経路を足した（M-63）。
受け付けるのは**ホスト側 G2P が出すのと同じ中間表現だけ**にする。

### 受け付けないものを、受け付けないままにした理由

漢字・カタカナ・句読点（`。` `、`）は**拒否する**。端末側で寄せない。

- 端末に辞書は載らない（B-0 / D-009。フル 102 MB、枝刈りしても 40 MiB 要った）
- **`。` を `#` に読み替える、といった「気を利かせた正規化」を端末に入れると、
  ホストが作る列と端末が作る列が食い違う。** 入力仕様（D-010 / D-011）の目的は
  「生徒が学んだ入力とデバイスが作る入力を一致させる」ことなので、
  端末だけが持つ規則を 1 つでも増やした時点で目的が崩れる
- 拒否は**位置と文字を出して**行う。⚠️ **未知語が無音で消えるのがこの系の
  一番危ない壊れ方**（B-0）なので、端末では黙って落とさない

漢字混じり文からの変換は `scripts/to_intermediate.py`（ホスト・OpenJTalk）。
このスクリプトは**出した行の往復一致をその場で検査**して、
一致しなければ終了コード 1 を返す（中間表現は人が読めてしまうので、
間違っていても「それらしく」見えるため）。

### 上限は 350 ids。**arena の限界 (520) ではない**

`make -C csrc arena` では 208 KB の arena で n_ids 520 まで通るが、**受け付けない**。

- 生徒が学習したのは D-017 の `max_spec_length=700`（= 350 ids 相当）まで
- clip[1,80] の上限に張り付くと 350 ids で最大 28,000 frames = 325 秒になりうる
- **入力を拒否するほうが、分布外の音を黙って出すより良い**

同じ理由で、511 B を超える行は**切り詰めずに行ごと捨てる**。
先頭だけ喋ると「端末とホストで同じ列」が黙って崩れる。

### 起動時は **錨と照合するが、喋らない**（⚠️ 当日中に方針を変えた。C-039）

対話に入る前に、組み込みの中間表現を G2P して `demo_ids.h` の錨と照合する。
**これは必ず走る** — 錨との照合が「テーブルと実装がずれていない」唯一の機械的な証拠で、
ずれても音は出てしまうため。G2P だけなので 0.6 ms。

**その列で合成するのは既定では行わない**（`-DSAAN_BOOT_SPEAK=1` で戻せる）。
突き合わせの基準は同じ 1 文のままだが、**同じ中間表現を打てば bit 単位で同じ列になる**
ことを M-63 の T1 で確認したので、起動のたびに 1.2 秒の音声を作る理由が無い
（実機では 2.47 × RT の外挿でおよそ 3 秒の待ち）。

⚠️ **非対話ビルド（`SAAN_INTERACTIVE=0`）では既定で喋る。** ホスト stub の
ゲート 8 は `app_main()` の出力を golden と突き合わせるので、喋らないと
「27,136 sample vs 0 sample」で**常に赤になる**（`-DSAAN_BOOT_SPEAK=0` で実測）。

⚠️ 逆に、**発話ごとに PCM 統計を巻き戻す**必要が出た（`saan_i2s_pcm_reset`）。
巻き戻さないと 2 発話目の checksum が「1 + 2 発話目」になり、**値は出るので気づけない**。

### コンソールは UART0 と USB Serial/JTAG の両方に対応する

ESP32-S3 の DevKit には USB ポートが 2 つあり、**既定のコンソールは UART0**。
native USB 側に挿すと**ログは見えるのに入力が届かない**という、
テスターが最初に踏む形の失敗になる。両方をビルド時に選べるようにし
（`esp32/sdkconfig.usb_serial_jtag`）、`esp32/TESTING.md` に明記した。

⚠️ **VFS (`stdin` / `fgetc`) は使わない。** IDF v5.3 で
`esp_vfs_dev_uart_use_driver` → `uart_vfs_dev_use_driver` と名前が変わっており、
版によって綴りが違う。ドライバの API を直接叩けばその揺れを踏まない。

## C-039: 「起動時の 1 発話は消さない」は、根拠の半分を自分で潰していた

**2026-08-30、D-040 を書いたその日に撤回した**（ユーザー指摘）。

D-040 の初版は、起動時に錨の 1 文を合成する理由を 2 つ挙げていた:

1. 錨との照合が「テーブルと実装がずれていない」唯一の証拠
2. ホスト / QEMU / 実機を突き合わせる基準がこの 1 文

**どちらも「合成する」理由にはなっていなかった。**

- **(1) は G2P だけで済む。** 照合しているのは `saan_g2p()` の出力 ids であって
  音ではない。0.6 ms で終わる。合成は 1 ミリも寄与しない
- **(2) は同じ節の中で自分が潰していた。** M-63 の T1 で
  「デモ文と同じ中間表現を打つと**起動時と bit 単位で同じ checksum が出る**」ことを
  実測しておきながら、その直後に「対話入力は毎回違う列なので突き合わせに使えない」と書いた。
  **毎回違うのは「違う文を打ったとき」で、同じ文を打てば同じ列になる。**

対応: 錨との照合は残し、合成は既定で行わない（`-DSAAN_BOOT_SPEAK=1` で戻せる）。
プロンプトまで **601 ms → 85 ms**（QEMU の guest 時間）。

⚠️ **非対話ビルドでは既定で喋る**（ホスト stub のゲートが唯一の出力経路を失うため）。
このとき「ゲートが空虚に通る」と書きかけたが、**実測すると落ちる**
（`-DSAAN_BOOT_SPEAK=0` でビルドすると「27,136 sample vs 0 sample」で exit 1）。
空虚ではなく**常に赤になる**が正しい。書く前に測って直した。

**教訓**: 直前の段落で実証した事実が、次の段落の主張を無効にしていた。
**同じ文書の中でも、根拠は 1 つずつ「それはこの結論を支えるか」を見ること。**

1. **生成器が同時に書く。** 片方だけ更新される経路が無い

   `uv run python scripts/kana_g2p.py` が全 195 件を突き合わせる
   （piper-plus がある環境でのみ走る）

⚠️ **黙ってフォールバックすると、凍結テーブルが古いときに

`synthesize_student.py --intermediate` は piper-plus がある環境でも凍結テーブルを使う。

### 根拠

**1. 32 MB を選ぶ理由が無くなった。** ESP-IDF 5.5.0 のヘッダから、ESP32-S3 の
DBUS 窓は 32 MiB（`SOC_DRAM0_CACHE_ADDRESS_LOW/HIGH` = `0x3C000000`..`0x3E000000`）で、
**`SOC_EXTRAM_DATA_*` が同一レンジ = PSRAM が同じ窓を食う**。その結果:

- **N32R8V** でも素のフル辞書 25,880,002 B は窓 25,165,824 B を **714,178 B 超える**
- **N32R16V**（現行の 32 MB 品）は窓が **16,777,216 B** に落ち、最適化後のフル辞書
  16,128,887 B を置くと残り 648,329 B で **app すら入らない**
- フル辞書が成立するのは「32 MB flash + PSRAM 無効」だけ。**N32R8V は EOL**（B-0 §5）

**N16R8 では窓 25.1 MB > 物理 16 MB なので MMU は律速にならない。**

**2. OTA を捨てると 27% 多く入る。** 予算境界での内挿は禁止（C-009）なので

| **16 MB / A（OTA 無し）← 採用** | **370,863** | **303,501** |

**3. 辞書は教師が実際に引くものに合わせる。** このマシンには `sys.dic` が
3 リビジョンある（uv キャッシュ内の複製を除く）。`matrix.bin` / `char.bin` /

## C-051: 「未知語のフォールバックで枝刈りの被害が減る」は誤り

## D-044: 動作点を **438,750 entries / 接続行列は int16 のまま**にする

**判断 C（エントリ数）と D（接続行列を uint8 にするか）をまとめて決めた。**
D-042 の 370,863 を **438,750 に引き上げ、D は採らない。**

### 材料（M-77）

| entries | 行列 | blob | 枠の余り | **音素の誤り** | 新規実装 |
|---:|---|---:|---:|---:|---|
| 370,863（D-042） | int16 | 12,153,280 | 1,674,816 | 0.55% | なし |
| **438,750 ← これ** | **int16** | **13,702,320** | **125,776** | **0.32%** | **なし** |
| 528,750 | uint8 | 13,781,959 | 46,137 | 0.22% | **要** |

### なぜ 438,750 か

1. **改善の大半が取れる。** 0.55% → 0.32%（**−42%**）。
   残る 0.32% → 0.22% は **0.10 pt** で、そのために形式を変える価値は薄い
2. **新規実装が要らない。** uint8 形式はエンコーダと C リーダの両方に必要で、
   **全ゲートの再検証**が付いてくる
3. **余裕が 125,776 B（0.91%）残る。** 528,750/uint8 は **46,137 B（0.33%）**しかなく、
   辞書リビジョンが変わるだけで溢れる
4. **RAM は増えない。** 辞書は mmap で、**Viterbi の作業領域はエントリ数に依存しない**
   （24 KB で足りる。予算 48 KB）
5. **QEMU で通してある。** 漢字経路もかな経路も `0x78c209af06affc01`、
   DRAM の空きも 51,728 B で変わらない

### なぜ D を採らないか

**D は単独では価値が無い。** 1.89 MB 浮かせても、それを使う先が 528,750 しかない。
**C を 438,750 にした時点で D は不要**になる。

⚠️ **D の副作用も小さくない**: MeCab との一致が **3 / 1,696 文（0.18%）**落ちる（M-72）。
⚠️ 将来 528,750 を採るなら、**行ごとアフィン uint8** にすること
（対称 int8 は同じサイズで 0.53% 落ちる）。

### ⚠️ この決定が乗っていない前提

- **音として測っていない。** 「音素の 0.32%」は**ホストと違う音素の割合**であって、
  聴いた結果ではない。**聴取はゼロ**（K-8 の G32）
- **上限がある。** ホスト既定の後処理 3 段（ONNX / Sudachi / 踊り字）は端末に載らず、
  **中間表現で 2.00%** の文が食い違う（M-70 / C-049）。**エントリ数では埋まらない**
- **実機で動かしていない**

### D-042 との関係

**D-042 は撤回しない。** N16R8 / OTA 無し / 辞書 SHA-256 の凍結はそのまま。
**変えるのはエントリ数だけ**（370,863 → 438,750）。
パーティション表（`dict` = 13,828,096 B）も変えない。
`scripts/k1/dict_manifest.json` は辞書そのものの凍結なので**変わらない**。

## D-045: リリースは **latest だけで完結させる**。CI で機械的に検査する

### ⚠️ CI が初回で移植性バグを 1 件見つけた

`csrc` の job が Linux で落ちた。**CI の設定ではなくコードの欠陥**だった。

```
fft_test.c:27: error: 'M_PI' undeclared
fft_test.c:56: error: 'CLOCK_MONOTONIC' undeclared
```

## C-053: `int8_test` の W8A8 作業領域が M-58 のストライドに追従していなかった（テストの潜在バグ）

**2026-09-02、S4（blob v2）を入れたら `int8_test` の section 1 で `dec cup 12->76` と
depthwise の W8A8 が `nan` になった。** カーネルの変更のせいではなく、**テスト側の確保が小さかった**。

M-58 で活性化の行ストライドを `align16(cin)` にした。カーネル（`saan_conv1d_i8a` /
`saan_dwconv1d_i8a`）は `qx` に `align16(cin) × T` バイト書く。ところが `int8_test.c` は

**教訓**: **カーネルの契約（書く量）を変えたら、その関数を直接呼ぶテストの確保量を grep すること。**
`saan_conv1d_w` 経由（arena が `saan_act_scratch_needed` で数える）は最初から正しかった。

## D-046: 速度改善の出力基準 — **bit 同一か丸め水準かを先に宣言し、W8A8 は fp32 比 SNR の分布で判定する**。blob は **v2**

**2026-09-02。** 第三者の実機報告（M5Stack CoreS3 で W8A8+PIE **1.554× RT**。
[`research/s1-m5-cores3-speed.md`](research/s1-m5-cores3-speed.md)）を受けて、
積和以外の処理を削る S1〜S5a を入れた（M-80 / M-81、ブランチ `feat/s1-speed-m5`）。
そのとき**出力をどう守るか**を決めた。

### 決めたこと

1. **各ステップは「bit 同一」か「丸め水準」かを入れる前に宣言する。**
   bit 同一（S1 検索の集約 / S4 blob v2 / S5a PIE ループ）は checksum 不変で示す。
   丸め水準（S2 量子化の逆数乗算 / S3 GELU の erf 近似）は `|max|` 完全一致 + Σx² 相対差 ≤ 1e-6 で示す
2. **W8A8 だけは 2 の判定が使えない。** 量子化の境界で 1 値が ±1 変わると下流 5 段に伝播し、
   |max| が 1% 動く（S3 で 9744 → 9627）。**判定は fp32 比 SNR（held-out 24 文の平均 / 最小）が
   0.1 dB 以上下がらないこと**（M-55 で SNR 23 dB でも SCOREQ 差なしと分かっている）。
   S2 は 24.24 → 24.21、S3 は 24.21 → 24.21 だった
3. **QEMU の基準 checksum は S3 で更新する**: W8A8+PIE `0x04de91103a0e49f9` → **`0xa69a7ebbb5ccb05f`**、
   W8A32 `0x78c209af06affc01` → **`0xe4b645c30835d42d`**。旧値は v0.2.0 までの配布イメージの値として残す。
   手順書（`esp32/TESTING.md` / `esp32/boards/m5unified/README.md`）は**両方書く**
4. **blob は v2**（int8 conv 重みを `[cout][k][align16(cin)]` で 0 埋め。654,032 B）。
   **int8 を含む v1 blob はコアが `SAAN_ERR_VERSION` で拒む**（fp32 だけの v1 = golden / ids は読める）。
   v1 の重みを v2 のカーネルが読むと**黙って別物の音**が出る（名前は同じで区別できない）ので、
   フォールバックにしない
5. **リリース資産 `saanotts-jp-v3-int8.bin` の v2 化はマージ時に行う**（D-045 = latest だけで完結。
   それまで README / TESTING.md に「資産は v1。S4 以降のコアには v2 が要る」と書いておく）
6. **S5b（重み行を QR レジスタに保持）と D-048（W8A8+PIE を既定にするか）は実機の表を見てから。**
   QEMU の命令数比（1 step −49%）はサイクルではない

### ⚠️ この決定が乗っていない前提

- **実機の速度は 1 つも自分で測っていない**（第三者の報告 2 件: CoreS3 1.554〜1.558 / AtomS3 1.718。どちらも配布 firmware = S1 前のコア）。板はユーザーのスタックチャン（種類未同定）
- S2 / S3 の知覚評価（SCOREQ）は取っていない。SNR の不変と M-55 からの推論
- QEMU が PIE の併合形（`ee.vmulas.s8.accx.ld.ip`）を実機と同じ意味論で実装している保証は無い。
  **実機の checksum が `0xa69a7ebbb5ccb05f` になるかで分かる**

## C-055: 「命令数が減った」「マイクロベンチで速かった」は実機の速さの証拠にならない — T5-G3 の符号ビット OR で GELU が 2 倍遅くなっていた

**2026-09-03。** S2 計画の T5（GELU のコード生成）を 4 コミットに分けて入れた。それぞれ QEMU の checksum は基準と bit 一致し、
G-3（FP 分岐 2 つを消す）は objdump で命令数が 70 → 59 に減り、pie_probe の E 節（M-85）は「erf のインライン化で 112 → 74.5 cyc/要素」を示していた。
**マージして実機に載せたら GELU は 118 → 211 cyc/要素で、1 step が 14.7% 遅くなっていた**（M-87）。

原因は G-3 の「`x < 0 ? -y : y` を `memcpy` による符号ビットの OR に置き換えた」1 か所。GCC 14.2 for Xtensa は
FP → 整数 → FP の往復を `rfr` / `wfr` ではなく**スタック経由の store → load** に落とし、in-order の LX7 で要素ごとに止まる。
T5 の実装者は objdump でそれに気づいて notes に「残る無駄: 符号の bit 演算がスタック往復に落ちている」と**書いていた**が、
「命令数が減った」ことを主な成果として報告し、私もそれを通した。

**なぜ検出できなかったか**:

| 手段 | 結果 | 見えなかった理由 |
|---|---|---|
| QEMU の checksum | 一致 | 値は正しい。時間の問題 |
| QEMU の cyc | — | 命令数に比例（M-80 → M-82 で分かっていた） |
| objdump の命令数 | 70 → 59 | store → load の依存は命令数に出ない |
| pie_probe E 節（M-85） | 74.5 | **旧形（三項演算子）をインライン**した写しで、新形（memcpy）は測っていなかった |
| ホストの all-test / erf の全走査 | 通る | 別 ISA |

**直したこと**: 三項演算子に戻した（2cab5aa）。クランプ・事前スケール表・インライン化・DRAM 配置はそのまま。
GELU 73.09 cyc/要素（E3 の 74.5 と一致）、1 step 16.64 M cyc（M-84 の 17.13 M から −2.8%）。

**教訓**:
- **速度の主張は、その形のコードを実機で測った数字だけ。** 命令数・QEMU・「似た形」のマイクロベンチはどれも根拠にならない。
- **実装者の notes の「⚠️ 残る無駄」は、成果より先に読む。** 今回は答えが書いてあった。
- **マージ直後に PROFILE=1 の表を 1 行ずつ前の版と並べる**（M-87 §1 の表）。GELU 行だけ見れば 10 秒で分かる。この手順を S2 計画の実機セッションに固定する。
- **マイクロベンチ（E 節）に「これから入れる形」を先に足す。** 1 回 10 秒。入れてから測るのは順序が逆。

## C-056: ゴールデンテストは **NaN を「完全一致」と報告して通していた**（2026-09-03）

**CI の網羅を点検していて踏んだ。** リリースの fp32 資産で `golden_test` を動かせるか試すついでに、
陽性対照として `student.bin` を 4 バイト壊したところ、こう出て**通った**:

```
OK  out.pcm   Pearson 1.000000  SNR     inf dB  max|Δ| 1.684e-03  n=27136
参照実装と一致（Pearson >= 0.98 かつ SNR >= 40 dB）
```

`err == 0`（SNR が inf）と `max|Δ| = 1.684e-03`（誤差がある）は**両立しない**。
実際には出力の **27,136 サンプル中 26,368 が NaN** だった。

**なぜ通ったか** — `csrc/golden_test.c` の `compare()` に落とし穴が 2 つ:

| 式 | NaN のとき | 結果 |
|---|---|---|
| `err > 0 ? 10*log10(sig/err) : INFINITY` | `NaN > 0` は **false** | INFINITY 分岐 = 「誤差ゼロ」 |
| `(da > 0 && db > 0) ? num/sqrt(da*db) : 1.0` | 同じく false | Pearson **1.0** = 「完全相関」 |
| `if (fabs(e) > mx) mx = fabs(e)` | 同じく false | max\|Δ\| は NaN 以外の最大値が残る |

**3 つの指標が揃って「完全一致」に化ける。** しきい値（Pearson ≥ 0.98 / SNR ≥ 40 dB）は正しいのに、
NaN がその手前で判定を素通りしていた。**NaN を出す退行はこのゲートでは捕まらなかった。**

**直したこと**: `compare()` が非有限（NaN / inf）の要素数を数え、1 つでもあれば落とす。
`err` が NaN のときの SNR は INFINITY ではなく NaN にした（`NaN >= 40.0` は false なので、しきい値でも落ちる）。

```
NG! out.pcm   Pearson 1.000000  SNR     nan dB  max|Δ| 1.684e-03  ← 非有限（NaN / inf）を含む
    非有限 26368 / 27136 要素（**NaN は Pearson 1.0 / SNR inf に化ける**）
```

**教訓**:
- **「一致」を返す既定値を持つ比較関数は、退化した入力で必ずそれを返す。** `err > 0` / `da > 0` のような
  「正常なら真」の条件を分岐に使うと、**NaN は全部 else 側に落ちる**。else 側を「一致」にしてはいけない。
- **陽性対照は「出力を壊す」だけでなく「入力（重み）を壊す」でも試す。** このゲートには
  参照出力を壊す陽性対照はあった（それは効いていた）が、**重みを壊す対照が無かった**。
- 矛盾する 2 つの数値（SNR inf と max\|Δ\| ≠ 0）が並んだら、**どちらかではなく判定自体を疑う**。

**再発を防ぐ仕掛け**: `golden_test` に**毎回走る陽性対照**を組み込んだ（このゲートには自前の陽性対照が
無かった。それが 1 か月気づかなかった理由）。実データの複製に (1) NaN を 1 個混ぜる (2) 振幅を 0.5 倍する
の 2 つを当て、**どちらも落ちること**を確かめる。(2) を入れたのは **Pearson がスケール不変**だからで、
SNR が効いていないと (2) は素通りする。

検証: 比較器だけを C-056 以前の式に戻すと、この陽性対照が
`NG! 陽性対照: NaN 1 個 → **通ってしまう**` を出して `exit=1` になる（自分で実行して確認）。
