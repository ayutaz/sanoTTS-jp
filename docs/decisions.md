## D-001: 教師は piper-plus の `.ckpt`。ONNX は使わない

- **日付**: 2026-08-26
- **決定**: `SynthesizerTrn.infer()` を PyTorch で呼ぶ

**理由**: ONNX export は `output` と `durations` しか出さず、蒸留に必要な**潜在 `z` が
取れない**（M-7）。`infer()` は `InferOutput(audio, attn, y_mask, (z, z_p, m_p, logs_p), durations)`
を返し、これが論文の `yT` / `zT` / `dT` にそのまま対応する。

## D-003: piper-plus は HEAD (v2.0.0) をそのまま使う

- **日付**: 2026-08-26
- **決定**: `v1.13.0` への checkout も worktree も**しない**

**理由**: 当初「公開 base ckpt は FiLM 化で size mismatch する (Issue #616) ので
`v1.13.0` が必要」と考えたが、**実測したら不要だった**（M-2.4）。

- ckpt の `spk_embed_dim=192` で v2.0 の 192 次元チェックを通る
- `dec.cond.weight` が `(512,512,1)` + `cond_layers` あり = **元から post-FiLM**
- `load_state_dict` が **missing 0 / unexpected 0**、`cond_migrated=0`

むしろ `v1.13.0` に落とすと pre-FiLM 想定になって size mismatch する。

**運用**: piper-plus のリポジトリは**読み取り専用**で扱う（checkout / commit / 編集をしない）。
`sys.path.insert` で `src/python` を先頭に置く（M-1.1 の stale install 対策）。

## D-004: `speaker_embeddings=None` を渡す

- **日付**: 2026-08-26
- **決定**: ラベル生成では `None`。`eval/spk_tsukuyomi.npy` は渡さない

**理由**: この ckpt は `num_speakers=1` で `spk_proj` / `emb_g` を state_dict に 1 件も持たず、
**None / npy / ランダム 192 次元 の 3 通りで audio が bit 完全一致する**（M-3.1）。
何を渡しても無視されるので、意図を明示するために `None` を渡す。
話者はすでに重みに焼き込まれている。

## D-005: 音素化は `text_to_phoneme_ids_and_prosody` に `language_id_map` を渡して呼ぶ

- **日付**: 2026-08-26
- **決定**: 自前で音素→ID 変換を組まない

**理由**: `language_id_map` を渡すと multilingual に auto-promote され、
**トークン間に `_` の intersperse padding が入る**（`len(ids) ≒ 2*tokens+3`）。
これを飛ばすと**発話が約 2.4 倍速になる**（17.7 mora/s vs 正常な 7.6〜8.4、M-5）。

加えて自前実装は PUA 変換（M-4.2）を間違えやすく、間違えても例外が出ない。

## D-007: ターゲットは ESP32 のみ。ブラウザは対象外

- **日付**: 2026-08-26（ユーザー判断）
- **決定**: 567 K embedded tier が唯一の成果物。1.4 M は検証用の足場

**理由**: **ブラウザは piper-plus の WebAssembly で既に解決済み**なので、そこを
再実装しても価値がない。「ESP32 に対応できなければ意味がない」。

**この決定が計画に与えた影響**:

| 項目 | 変更前 | 変更後 |
|---|---|---|
| 成果物 | 1.4 M quality (browser) を優先 | **567 K embedded (ESP32)** |
| 1.4 M の位置づけ | 本命 | **足場**（レシピが日本語で効くかの確認と、567 K との差分測定） |
| オンデバイス G2P | 「音素ID入力に割り切る」で回避 | **回避不可。成立しなければプロジェクトが無意味** |
| 最優先タスク | ラベル生成の疎通 | **B-0（G2P フットプリント spike）** |

**根拠となる観測**: 辞書 102 MB のうち **65.2% が feature 文字列**で、TTS には不要な
品詞・活用情報が大半（M-8）。枝刈り + feature 削減で数 MB に収まる可能性があり、
「102 MB だから不可能」という初期判断は雑すぎた。ただし線形概算なので B-0 で実測が必要。

**判断分岐**: B-0 で「数 MB で実文の 95%+ が正しく読める」が示せなければ、
入力境界の再定義（かな入力限定 / 定型文プリコンパイル / ホスト側 G2P）か
プロジェクト自体の見直しになる。

## D-009: B-0 の結論 — G2P は端末に載せず、入力境界を音素ID列に置く

- **日付**: 2026-08-26
- **状態**: **測定完了。ユーザー判断待ちの論点が 3 つ残る**
- **一次データ**: [`research/b0-g2p-footprint.md`](research/b0-g2p-footprint.md),
  `reports/b0_{size,coverage,alternatives,flash_budget,feature_fields}.json`

### 測定結果（すべて実ビルド + held-out 2,325 文）

| 問い | 答え |
|---|---|
| 16 MB ボード + OTA 2 枠 (11.73 MB) に収まる最大辞書 | **60k表層 +guard+noread = 11.57 MB** |
| その一致率 | **文単位 73.0%** / トークン単位 PER 2.36% (= **97.6%**) |
| 文単位 95% に必要な辞書 | **400k entries = 40.05 MiB** → **32 MB ボードにも入らない** |
| アクセント込み 95% | **400k / 40 MiB でも 89.29%。届かない** |

### さらに根本的な制約（辞書サイズと無関係）

教師の G2P (`pyopenjtalk.extract_fullcontext`) は **pyopenjtalk-plus の Python 後処理層**
（SudachiDict 207 MB + nani ONNX）を**デフォルトで通る**。これは ESP32 に載らない。
C 実装のみ (`use_vanilla=True`) に落とすと、**フル 103 MB 辞書でも**:

- 音素列 **95.4%**（自己実測 800 文。うち無声化のみの差が 1.88% なので、それを許容すれば 97.25%）
- アクセント **76.2%**（レポート、アクセント句単位）/ **84.0%**（自己実測、A1 単位）

**これは辞書を大きくしても縮まない下限。** ただし M-11 の通り、
**ラベル生成側も `use_vanilla=True` に揃えれば原理的に消える**（要検証）。

### 決定

**蒸留の入力境界を音素ID列に固定する**（論文 §II の "external G2P excluded" と同じ境界）。
CLAUDE.md の既存の判断が本 spike の実測で裏付けられた形。

- ホスト側 G2P: 端末フットプリント **0 B**、精度は教師と同一、回線 **68 B/文**
  （音声を Opus で流すより 2 桁小さいので「端末で合成する」利点は失われない）
- 完全スタンドアロン用途は**定型文プリコンパイル**: 1 B/音素、通知系 **40.4 B/文**、
  1,000 文で 40 KB。同じ文を PCM で焼くより 3,228 倍小さい
- **辞書枝刈りは実装対象から外す**

### 実務的に最も価値のある発見: guard set

頻度枝刈りをすると**全角数字が落ちて数値が無音で消える**。
`午後3時15分です。` → `ゴゴ、ジ、フンデス`（`９` は 60k 辞書にも入らない）。

未知語は**誤読ではなく無音で脱落する**（`unk.dic` の 40 エントリは読み・アクセントを
一切持たないため `、` に置換される）。例外も警告も出ない。

対策は「名詞,数」279 + 「*,接尾」2,254 + 「記号,*」202 = **2,705 表層形の強制追加**。
30k 水準で +531 KB の費用に対し、embedded セットの音素列一致が
**28.96% → 80.87%（+51.9pt）**、無音化 token が 194 → 27 instance。

**枝刈り路線を採らなくても、この「未知語は無音で消える」性質は
入力サニタイズの設計に効く**（外字・幽霊漢字はホスト側 G2P でも同じ失敗をする）。

### ⚠️ ユーザー判断が必要な 3 点

1. **「目安 95%」は文単位かトークン単位か。** 文単位なら「入力境界の再定義」、
   トークン単位なら 30k / 7.13 MB でも合格し「枝刈り続行」もあり得る。**判定が反転する**
2. **OTA を要件に含めるか。** 含めなければ 16 MB ボードの辞書枠は 11.19 → 13.19 MiB
3. **任意テキストを喋る必要があるか、定型文＋数値スロットで足りるか。**
   後者なら辞書問題は消える

### ⚠️ go/no-go を出す前に必要な残測定

- **RAM ピークとレイテンシが完全に未測定。** flash に入っても OOM すれば落ちる。
  ESP-IDF がこのマシンに無く、xtensa ビルドもしていない
- **B-1 との経路不一致**: B-0 は `JapanesePhonemizer`/`pyopenjtalk` 基準だが、
  教師の canonical 経路は `MultilingualPhonemizer`。かな無し行 5.72% が中国語に誤ルーティング
  される問題の上に全数値が乗っている

## D-010: ひらがな入力仕様 — 読みは 1.6 KB で解決、アクセントは入力に持たせる

- **日付**: 2026-08-26（ユーザー提案）
- **状態**: 測定完了。**D-009 の結論を部分的に覆す good news**
- **一次データ**: [`measurements.md`](measurements.md) M-12

### 提案

「漢字・カタカナを除外し、**ひらがなのみ入力**を受け付ける仕様に変更する」

### 測定結果

**読みは解決する。** かな→音素は決定的な規則で、**mora テーブル 1,644 B**。
無声化を正規化した PER は **0.272%**。40 MB の辞書が 1.6 KB の表になる。

**アクセントは解決しない。しかも辞書を積んでも直らない**（自己実測 500 文）:

```
漢字かな交じり → ひらがな化 → フル 103MB 辞書で再解析
  音素列    一致 84.00%
  アクセント 一致 15.00%   ← 辞書サイズと無関係
```

原因は分割の曖昧性であってサイズではない。かなにすると語境界と語義が失われるので
Viterbi でも復元できない。**かなキーのアクセント辞書を積んでも上限は同じ 15%。**

### 決定

**アクセント記号を入力に含める。** `[`（上昇）/ `]`（下降核）/ `#`（句境界）は
**すでに音素列のトークン**なので、入力がこれを持てば端末側の推論が不要になる。

| 案 | 端末フットプリント | アクセント精度 |
|---|---:|---|
| **ひらがな + アクセント記号** ← 採用 | **~2 KB** | **教師と同一** |
| ひらがなのみ + かなアクセント辞書 | 0.16〜15 MB | 15%（上限） |
| ひらがなのみ・平板 | ~2 KB | 平板（棒読み） |

### D-009 との関係

D-009 は「辞書路線は成立しない → 入力境界を音素ID列に置く」だった。
D-010 はその**中間点**を作る:

- 音素ID列（D-009）: 端末 0 B、完全、だが人間が読めない
- **ひらがな + アクセント記号（D-010）: 端末 ~2 KB、完全、かつ人間が読み書きできる**
- 漢字かな交じり: 40 MB でも 73%

**ファームウェアに `でんき]をつけま]す` のような読める文字列を置ける**ことの
保守性の利益は大きい。定型文プリコンパイル（音素ID焼き込み）より扱いやすい。

### ⚠️ 未検証

- ひらがな + アクセント記号から音素ID列を組む実装を書いて、
  漢字版と bit 一致することを確認していない（M-12 は既存経路での測定）
- アクセント記号を人手で付けるコスト。**ホスト側で漢字→かな+記号に変換すれば自動化できる**
  （変換はオフラインで一度やればよい）
- 平板読みが実用に耐えるかの聴取評価
- カタカナ語をひらがなで書く際の表記ゆれ（`コンピューター` → `こんぴゅーたー`）

## D-011: 入力仕様を確定 — ひらがな + アクセント記号 + 無声化マーク

- **日付**: 2026-08-26（ユーザー決定）
- **状態**: **確定。要件定義書 [`requirements.md`](requirements.md) に反映済み**

### 決定

本プロジェクトの入力は **中間表現「ひらがな + アクセント記号 `[` `]` `#` + 無声化マーク `°`」**とする。
漢字かな交じり文は端末で扱わない。

### 根拠（すべて実測）

| 方式 | 往復一致率 | 端末フットプリント |
|---|---:|---:|
| ひらがなのみ（フル 103 MB 辞書でアクセント推定） | 15.0% | 103 MB |
| ひらがな + アクセント記号（無声化は規則） | 59.6% | 951 B |
| **ひらがな + アクセント記号 + 無声化マーク** | **100.0%** | **951 B** |

無声化を規則で推定すると **170 箇所を過剰無声化**した。品詞とアクセント型に依存するため
規則化できない。→ **入力に持たせる**。

### これで解決したこと

- 辞書 40 MB → **951 B**。8 MB フラッシュのボードでも余裕
- アクセント精度が教師と同一（記号は音素IDそのもの）
- **ファームウェアに人間が読み書きできる文字列を置ける**（音素IDのバイト列より保守しやすい）

### 副次的な確認: アーキテクチャの変更は不要

アクセント記号は音素ID 8 / 9 / 7 で、英語の強勢記号 `ˈ`(87) `ˌ`(88) と同じ機構。
VITS はピッチを潜在 z に持ち、z は音素IDから決まる。記号位置を1つ変えると
F0 が **42.8 Hz** 変わることを実測（M-13）。**生徒に韻律入力を足す必要はない。**

なお `prosody_features` (A1/A2/A3) は duration predictor にしか入らず、
ピッチには影響しない。論文の生徒設計（acoustic は音素IDと duration のみ）は日本語でも正しい。

## D-012: Python は uv、学習は vast.ai

- **日付**: 2026-08-26（ユーザー決定）
- **状態**: 確定。`pyproject.toml` / `uv.lock` を作成し動作確認済み

### uv

```bash
uv sync ; uv run python scripts/xxx.py ; uv add <pkg>
```

piper-plus は `[tool.uv.sources]` の **path 依存 (editable)** で参照する。
**piper-plus のリポジトリは読み取り専用**（D-003 の運用を継続）。

**副次的な利益**: uv の独立 venv には M-1.1 の stale な `piper_train`（v1.13.0 相当、
`piper_plus_workspace-1.12.0` の所有物で `pip install -e` では消えない）が
**存在しない**ため、`sys.path.insert` なしで正しいモジュールが解決される。

**環境差の検証**: piper-plus venv (py3.13.9/torch2.11) と uv 環境 (py3.14.0/torch2.13) で
**教師ラベルが bit 完全一致**することを SHA-256 で確認した（M-15）。
バージョンが上がってもラベルは変わらない。

### vast.ai

ローカル（macOS / MPS）では学習しない。**ラベル生成も vast.ai 側で実行する。**

理由はデータ量の非対称性:

| | サイズ |
|---|---:|
| 学習テキスト | **1.2 MB** |
| ラベルパック (fp16+int16) | **4.42 GB** |
| ラベルパック (fp32) | 8.83 GB |

ローカルで生成して 4.4 GB をアップロードするより、テキスト 1.2 MB を渡して
向こうで生成するほうが桁違いに安い。教師 ckpt (927 MB) は HF から直接取得できる。
ラベルが環境非依存で bit 一致することは上記で確認済みなので、この分割は安全。

インスタンス要件は [`requirements.md`](requirements.md) §8.4。

### ⚠️ 未検証

**GPU 推論が CPU と bit 一致するかは未確認**（M-15 の照合は CPU 同士）。
TF32 や異なるカーネルで差が出る可能性がある。したがって:

1. ラベル生成は**一度だけ**実行し、パックに SHA-256 を付けて固定する
2. 生成環境（Python / torch / CUDA のバージョン）を manifest に記録する

## D-013: 品質は「教師比」と「人間音声比」の両方で報告する

- **日付**: 2026-08-26
- **一次データ**: [`measurements.md`](measurements.md) M-10

### きっかけ

教師の UTMOS が 1.748 と出た。論文の教師 4.42 と比べると壊滅的に見えるが、
**実人間の日本語音声（教師の元コーパス）を測ったら 2.305 しかなかった。**

同一エンジンで言語だけ変えた piper-plus のデモ音声でも
ES 3.51 / EN 2.97 / FR 2.23 / ZH 1.80 と系統差が出る。
UTMOS は VoiceMOS 2022 の BVCC（英語）/ BC2019（中国語）で学習されており、
**日本語ではスケールが圧縮されている**。

### 決定

品質指標は次の 2 つを併記する。**絶対値は報告しない。**

```
教師比   = 生徒 / 教師           ← 論文と同じ土俵で比べるため
人間比   = 生徒 / 実人間音声      ← 指標の較正ずれを吸収するため
```

人間音声の分母は**教師の元コーパス**（つくよみちゃんコーパス）を使う。
話者・録音条件が教師と揃っているので、比の解釈が素直になる。

### 現時点の位置

```
教師 / 実人間 = 1.748 / 2.305 = 0.758
```

## D-014: ラベル生成の入力は中間表現。prosody はゼロ

- **日付**: 2026-08-27（Phase A / B の実測で決着）
- **一次データ**: `docs/plan/phase-a-decisions.md` / M-19 / M-20

### 入力経路

```
漢字文 ──[ホスト・OpenJTalk]──▶ 中間表現 ──[kana_g2p]──▶ 音素ID ──▶ 教師 ──▶ ラベル
                                              ↑ デバイスと同じ変換器
```

**生徒が学ぶ入力とデバイスが作る入力を一致させる**のが理由。副産物として
**B-1（かな無し行 5.36% が中国語音素になる問題）が構造的に消えた**。

### prosody

**ゼロを渡す。** held-out 無作為 24 文で UTMOS を比較すると
canonical + 実 prosody 1.730 / 中間表現 + zeros 1.740 で **有意差なし（p=0.72）**。

- デバイスは prosody を供給できないので、教師と生徒の条件が揃うほうが良い
- 実 prosody は ID 列の 92% で位置合わせできない
- prosody は duration にしか効かず、ピッチはアクセント記号が担う（M-13）

⚠️ ゼロは「prosody 無し」ではない。`prosody_proj(0) = bias` が concat される
第 3 の条件で、**それで一貫させる**という決定。

### PAD 規則

canonical (`PiperEncoder._post_process`) と同一にする:
**「その音素自身が PAD なら後ろに PAD を挟まない」**。
これを外すと音素ID一致が 86% → **0%** になる（例外は出ない、M-20）。

## D-016: デプロイ語彙は 57。浮いた 8,000 params は width に回さない

**日本語のデプロイ語彙は 57 トークン**（論文の英語版は 157）。
`kana_g2p` の mora テーブル + `ん` の異音規則 + 無声化 + 長音 + 記号から
**原理的に出せる音素の閉包**であって、コーパス出現 51 の上位集合（M-26）。
コーパスに出ただけの語彙で凍結すると、実運用で未出現の音素が来た瞬間に壊れる。

`VOCAB` 157 → 57 で **567,008 → 559,008 params**（−8,000, −1.41%）。

**浮いた 8,000 params は width に回さない。** 理由:

1. **語彙削減で MMAC は 1 も減らない**（埋め込みは表引きで 0 MAC）。浮いたのは
   flash 8 KB だけで、flash は逼迫していない
2. width に回すと **MMAC は増える方向にしかならない**（+0.20〜+0.53 MMAC/s）。
   ESP32 で逼迫するのは flash ではなく実時間
3. 8,000 params は総量の 1.41%。品質への寄与は測れないほど小さいと見込まれる

⚠️ **生徒は教師の音素ID をそのまま埋め込みに使えない。** 57 トークンの教師 ID は
最大 64 で 8 個の穴がある。`src/saanotts_jp/vocab.py` の `TEACHER_TO_STUDENT` を
必ず通す。**この写像表は重みと一緒に凍結する。**

⚠️ **当初 6 トークンのコーパス出現が 0 だった。3 つは解消済み。**
- `?!` `?.` `?~` は**ホスト G2P が原文の約物から出す**ので到達可能なのに、
  コーパスに 1 行も無かった。**疑問 EOS 4 種を含む実文 47 行を足した**
  （`scripts/b9_add_question_eos.py`、train 39 / heldout 8）。使用音素 51 → 54。
  併せて `〜`(U+301C) が `?~` にならず**約物が黙って消える**問題を
  `kana_g2p.normalize_input()` で塞いだ
- **`A` `E` `O` は残る。** 無声化母音だが日本語の母音無声化は狭母音 `i` `u` に
  ほぼ限られるので実データに出ない（C-004）。未学習行を残さないよう
  `a` `e` `o` と**同値初期化**する

## D-018: `_` PAD は他のトークンと同じ扱いにする（D2 の決着）

**当初の懸念**: 「トークンの 49% が PAD なら、`Dα` の実効トークン予算の半分が
PAD に消える。PAD を別ヘッドにするか、除いた列で学習して推論時に再挿入するべきか」

**却下する。PAD を特別扱いしない。** 実測がそろって逆を指している（M-25 / M-27）:

| 事実 | 値 |
|---|---:|
| PAD のトークン比 | 50.02% |
| **PAD のフレーム比** | **53.76%** |
| PAD の duration mean | **2.059**（実音素は 1.697） |

duration を軽く見積もる設計にすると音の過半を捨てることになる。

## D-019: `s_v = 1.2187` を初期値にする（量子化ぶんのみ。学習後に解き直す）

`s_v` は**言語固有の話速ではなく、丸め規約の差を吸収する係数**（M-24）。
教師は `w_ceil = ceil(w)` でフレームを割り当て、生徒は
`d̂ = clip_[1,80](round(s_v · r))`。この 2 つの比が `Σceil/Σclip(round) = 1.2277`。

コーパス全体で総フレームを一致させると **`s_v = 1.2187`**、発話ごとの比は
mean 0.9984 / sd 0.0206 に収まる（`s_v=1.0` では 0.8135）。

⚠️ **反証された旧説と数値が近いが、根拠は別物。** 旧説の「1.2 前後」は
B-1 の誤ルーティングで壊れた 1 文の SDP サンプル比から出ていて、量とし
ても別物だった。**偶然近いだけ**なので、旧説を復活させないこと。

⚠️ `r_i` に生徒の予測ではなく `dT` を代入している（完璧な生徒の仮定）。
**学習後に生徒の予測で解き直す。**

**`clip_[1,80]` について**: 上限 80 は飽和しない（max ceil 30）。
効いているのは**下限 1** で、`dT < 1` が 18.49%、うち実音素が 290,692 個。
99.96% の発話が該当トークンを含む。

## D-021: λ は勾配整合で初期化し、`λ_n` / `λ₂` は実行時に計算する

論文が公開しているのは `(λ_w, λ_S, λ_A, λ_F, λ_c) = (0.1, 0.5, 0.025, 0.25, 0.5)` だけ。
`L_c` の内訳は "the weighted sum implemented by the trainer" としか書かれていない。

**「全部 1.0」は誤りだった**（M-30）。実 `zT` に対する勾配ノルムを `l1` に揃える:

| λ | 値 | 出し方 |
|---|---|---|
| `λ_n` | 0.272 | **実行時**に `ChannelStats.lambda_n` = `1/√(mean(1/σ_k²))` |
| `λ₂` | — | **実行時**に残差 RMS から `1/(2·RMS)`。結果として L2 が RMS 項になる |
| `λ_Δ` | **0.86** | 定数（探索対象） |
| `λ_s` | **0.19** | 定数（探索対象） |
| `λ_T` | **0.27** | 定数（探索対象） |

**`λ_n` と `λ₂` を定数で焼かない。** `λ_n` は σ 依存でパックが変われば
0.37〜0.46 倍ずれる。`λ₂` は残差依存で、**学習が進むほど大きくなる**
（初期化時 0.397 → 収束するほど上昇）。「2.0 から減衰」は方向が逆。

**式2 のターゲットも直した**。`r = max(1, exp(l̂))` に clamp があるのに
ターゲットが `Σ dT` のままだと、`dT` の 18.49% が 1 未満なので**完璧な生徒でも
length 項が 0 にならず、発話を 4.4% 短くする定常バイアス**になる（C-021）。
`Σ max(1, dT)` にして自己整合させた。

**残る探索対象は `λ_Δ` / `λ_s` / `λ_T` の 3 つ**（`λ_n` `λ₂` は閉形式で不要）。

## C-020: hook が改行を跨いで誤検知した（C-015 と同じ根の再発）

**何が起きたか**: 次のコマンドが deny された。

```bash

chmod +x deploy/vastai_bootstrap.sh
```

`chmod` は 2 行目、piper-plus のパスは 3 行目なのに、**同一コマンドと見なされた**。

回帰テストを 39 → **47 ケース**に増やした。

**教訓**: **区切り文字の定義は 1 か所にまとめる。** 2 か所に散らしたので片方だけ
直して同じバグを再発させた。

## C-021: 「λ を全部 1.0 で置く」→ 勾配ノルムが桁で違う

**書いたこと**: `losses.py` に `LAMBDA_2 = LAMBDA_N = LAMBDA_D = LAMBDA_STAT

`λ₂` は残差依存（固定値が存在しない）。**1.0 は「中立」ではなく、

**なぜ間違えたか**: 「論文に無いから 1.0」は**値を決めていない状態を隠す**書き方
だった。1.0 も 1 つの選択であって、選んだ以上は測るべきだった。
