## 1. 背景と目的

### 1.1 なぜ作るのか

論文 sanoTTS は、567,008 パラメータの TTS を ESP32-S3 上で **0.22× リアルタイム**で動かした。
英語・ベトナム語・インドネシア語で実証されているが、**日本語版は存在しない**。

piper-plus はブラウザ (WebAssembly) では既に日本語 TTS を実現している。
したがって本プロジェクトの価値は **ESP32 で動くこと**にのみある。
ブラウザ向けの再実装には価値がない。

### 1.2 何が障壁だったか

日本語 G2P（OpenJTalk + NAIST-JDIC）は **102 MB** で ESP32 に載らない。
実測の結果、枝刈りでも解決しないことが分かった:

| 辞書サイズ | 文単位の音素列一致率 |
|---:|---:|
| 11.57 MB（16 MB ボードに載る最大） | 73.0% |
| 40.05 MiB | 95.5%（**32 MB ボードにも入らない**） |

さらに教師の G2P は Python 後処理層（SudachiDict 207 MB）に依存しており、
C 実装のみに落とすと**辞書サイズと無関係に**アクセントが 16〜24% ずれる。

### 1.3 解決策

**入力仕様を「ひらがな + アクセント記号 + 無声化マーク」に変更する。**

漢字を扱わないので形態素解析が不要になり、辞書が **877 B の mora テーブル**に置き換わる。
アクセントと無声化は入力が持つので、端末側で推定しない。

```
漢字かな交じり文  ──[ホスト側・オフライン]──▶  中間表現  ──[端末側・877 B]──▶  音素ID列 ──▶ 音声
今日は良い天気ですね。                    きょ][おわよ][いて][んきです°ね
```

## 3. システム構成と境界

```
┌─ ホスト側（PC / ビルド時・オフライン）──────────────────────┐
│  漢字かな交じり文                                            │
│      ↓  OpenJTalk + NAIST-JDIC (102 MB)                     │
│  音素列 + アクセント                                          │
│      ↓  phonemes_to_intermediate()                          │
│  中間表現「きょ][おわよ][いて][んきです°ね」  ← これを端末へ渡す        │
└──────────────────────────────────────────────────────────┘
                              │ 平均 108 B/文
┌─ 端末側（ESP32-S3・実行時）───────────────────────────────┐
│  中間表現                                                    │
│      ↓  テーブル 877 B（mora 195 + 記号 10 + ん 異音 21）            │
│  音素ID列                                                    │
│      ↓  Duration Dα (32,964) → Acoustic Aβ (194,736)        │
│         → iSTFT Decoder Gγ (331,308)   計 559,008 params    │
│  22.05 kHz PCM                                              │
└──────────────────────────────────────────────────────────┘
```

⚠️ **論文（英語・語彙 157）は 567,008 params。日本語は語彙 57 なので 559,008**（D-016）。
埋め込みが 100 語彙 ×（Dα 32 + Aβ 48）= 8,000 減る。⚠️ **MMAC は 1 も減らない**（表引き）。

**境界の定義**: 論文と同じく「外部 G2P はシステム外」とするが、
本プロジェクトは**端末内に 877 B のテーブルだけで G2P を持つ**点で論文より広い境界を主張できる。

## 4. 入力仕様

### 4.1 中間表現の文法

```
中間表現 ::= ( モーラ | アクセント記号 | 境界記号 )*
モーラ   ::= ひらがな1〜2文字 [ "°" ]
```

| 記号 | 意味 | 音素ID |
|---|---|---:|
| `[` | アクセント上昇 | 8 |
| `]` | アクセント下降核 | 9 |
| `#` | アクセント句境界 | 7 |
| `°` | 直前モーラの母音を無声化 | （`i`→`I` 等） |
| `_` | ポーズ | 0 |
| `^` `$` | BOS / EOS | 1 / 2 |
| `?` `?!` `?.` `?~` | 疑問 EOS 4 種 | 3 ほか |

### 4.2 モーラ表

**116 エントリ / 877 B。** 清音・濁音・半濁音・拗音・外来語音（`ふぁ` `てぃ` 等）・
`っ`（促音）・`ん`（撥音）・`ー`（長音）を含む。

`ん` の異音は**後続子音から規則で決まる**（18 規則）:

| 後続 | 異音 |
|---|---|
| `m` `b` `p` `my` `by` `py` | `N_m` |
| `n` `t` `d` `ts` `ch` `ny` `ty` `dy` | `N_n` |
| `k` `g` `ky` `gy` | `N_ng` |
| その他・語末 | `N_uvular` |

`ー` は直前の母音を繰り返す。

### 4.3 なぜアクセントと無声化を入力に持たせるのか

**どちらも規則では決まらないことを実測で確認した。**

| 方式 | 往復一致率 |
|---|---:|
| ひらがなのみ（フル 103 MB 辞書でアクセント推定） | **15.0%** |
| ひらがな + アクセント記号（無声化は規則で推定） | 59.6% |
| **ひらがな + アクセント記号 + 無声化マーク** | **100%** |

無声化を「無声子音に挟まれた i/u」という規則で推定すると、実測で **170 箇所を過剰無声化**した。
無声化は品詞とアクセント型に依存するため規則化できない。

**アクセント記号は音素IDそのもの**であり、位置を1つ変えると F0 が **42.8 Hz** 変わる。
VITS はピッチを潜在 z に持ち、z は音素IDから決まるので、
**記号が入力にあれば生徒は正しいピッチを学習する。アーキテクチャの変更は不要。**

### 4.4 実測されたカバー率

| 評価セット | 中間表現で表現可能 | 往復の完全一致 | サイズ |
|---|---:|---:|---:|
| held-out 1,500 文 | **96.40%** | **100.00%** | 平均 108 B/文 |
| embedded 184 文（ESP32 実運用想定） | **98.91%** | **100.00%** | 平均 65 B/文 |

再現: `scripts/kana_g2p.py`

**表現できない 3.6%** は、アクセント句境界 `#` がモーラ内部（子音と母音の間）に
現れるケースが主。中間表現がモーラ単位のため表現できない。要調査（§9）。

## 5. 機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| F-1 | 中間表現を受け取り 22,050 Hz PCM を出力する | 必須 |
| F-2 | 端末側 G2P は mora テーブルと `ん` 異音規則のみで動作する（辞書・形態素解析を使わない） | 必須 |
| F-3 | アクセント記号 `[` `]` `#` を音素IDに透過的に渡す | 必須 |
| F-4 | 無声化マーク `°` を対応する無声化母音の音素IDに変換する | 必須 |
| F-5 | ホスト側変換器が漢字かな交じり文から中間表現を生成する | 必須 |
| F-6 | 未知文字を検出し、無音で脱落させずエラーとして扱う | 必須（§8.5） |
| F-7 | 疑問文 EOS 4 種を区別する | 推奨 |
| F-8 | ポーズ `_` による間の制御 | 推奨 |
| F-9 | **端末がシリアルから中間表現を 1 行受け取って合成する**（実装済み。M-63 / D-040） | 推奨 |
| F-10 | **端末側で受け付けない文字は、位置と文字を示して拒否する**（黙って無音にしない） | 必須（F-6 の端末側） |

⚠️ **F-9 / F-10 は後から足した**（2026-08-30）。当初はビルド時に焼き込んだ 1 文しか
喋れなかった。~~⚠️ **実機の UART では未検証**。~~ → **実機で検証した**
（[M-83](measurements.md#m-83) / [M-90](measurements.md#m-90)。CoreS3 の **USB Serial/JTAG** コンソールに行を打ち込んで合成した）。
⚠️ **UART0 では未検証**。~~⚠️ 配布イメージは UART0 入力で native USB の板では入力が届かない~~
→ ✅ **v0.3.0 で直した**（`-usbjtag` 版を併配し、M5 CoreS3 版は USB Serial/JTAG が既定）。
⚠️ **v0.2.0 以前のイメージは UART0 のまま**なので、CoreS3 / AtomS3 では入れ替えが要る（M-83 §1）。

## 6. 非機能要件

### 6.1 フットプリント

| 項目 | 目標 | **実測（2026-09-03）** | 根拠 |
|---|---:|---:|---|
| モデル (int8 blob) | **679,832 B**（論文の実績値） | ✅ **654,032 B**（blob v2 のファイル = v1 の 643,936 B + 事前整列の padding 10,096 B。うち重みの payload は 624,692 B） | [M-39](measurements.md#m-39) / [M-45](measurements.md#m-45) / [M-81](measurements.md#m-81) §7 |
| 端末側 G2P データ | **877 B** | ✅ **877 B**（mora 195 + 記号 10 + `ん` 異音 21） | `csrc/g2p_table.h` |
| 合計（フラッシュ） | **< 1 MB** | ✅ **654,909 B** | 上記の和（654,032 + 877） |
| RAM ピーク | **< 512 KB** | ✅ **arena 静的確保 180,224 B / 実測 used 157,360 B**。起動直後の内部 DRAM の空き **132,039 B** | [M-89](measurements.md#m-89) / [M-90](measurements.md#m-90) |

**8 MB フラッシュのボードでも大きな余裕がある。** 辞書路線で必要だった 11.57 MB が不要になった。

⚠️ **上の「合計」はモデルと G2P データだけの和で、app の総サイズではない。**
実機（M5 CoreS3、W8A8+PIE、`.rodata` に blob を埋めた構成）の **app は 1.43 MB**（factory 2.75 MB）。
⚠️ **かつて「RAM ピークは約 96 KB」と書いていた**（M-16 の解析値）。**実測は 157 KB** で、
差はストリーミングの窓と int8 の作業領域。**どちらも 512 KB 以内**なので判定は変わらない。
⚠️ **漢字を有効にすると桁が変わる**: 辞書 13.83 MB（438,750 entries）が要り、**16 MB flash が前提**になる（§2.2）。
内部 DRAM は漢字経路の作業領域 144,640 B を arena から切り出して足りている（M-90 §3）。

### 6.2 速度

⚠️ **この節の 2 項目はどちらも「分母が書かれていなかった」ことが後で問題になった。**
測ってみたら**分母の取り方で達否がひっくり返る**ので、両方を記録し、どちらを要件とするかは**未決**とする。
決めるのは **D-049**（`decisions.md`）。**勝手に有利な方を採らないこと。**

#### RTF（目標 ≤ 0.5。論文は 0.22）

| 分母の取り方 | **実測（CoreS3 / W8A8+PIE）** | 判定 |
|---|---:|---|
| **満チャンク 1 pull ÷ そのチャンクの音声長（92.88 ms）** | **0.446**（[M-90](measurements.md#m-90)、4 文とも 0.444〜0.447） | ✅ **達成** |
| **発話全体（全 pull の dt の和）÷ 音声長** | **0.541〜0.712**（M-90、n=4 文。M-88 では 0.550〜0.693） | ❌ **未達** |

**差は warmup**。受容野の 38 フレームぶんが初回 pull（**244.50〜244.66 ms**。[M-90](measurements.md#m-90)。
⚠️ **かな構成の M-88 / M-89 では 277〜279 ms**）に乗るので、
**文が長いほど発話全体の値は 0.5 に近づく**（1.231 s の文で 0.616、9.079 s の 4 文で 0.550）。
**アンダーランは全文で 0**、鳴らし始めまで **384 ms**（[M-90](measurements.md#m-90) §2 = 出荷構成。
⚠️ **かな構成では M-89 で 432 ms / M-88 で 434 ms**）。

⚠️ **論文の 0.22 がどちらの定義かは公開されていない**ので、「何倍遅い」を書くときは自分の定義を必ず添える。
⚠️ 経緯: 第三者の実機報告 **1.554**（2026-09-02、S1 前・旧定義。⚠️ **1.554 そのものは今も未再現**）→ 自分で 0.926
（[M-82](measurements.md#m-82)。⚠️ この値は末尾の端数 pull で膨らんでいた = [C-054](decisions.md)）→ **0.446**。
削ったのは積和ではなく、活性化の量子化 / GELU / テンソル検索 / 重みのコピー / 捨てる出力の計算だった（[M-80](measurements.md#m-80) / M-88）。
詳細は [`research/s1-m5-cores3-speed.md`](research/s1-m5-cores3-speed.md) §5。

#### 端末側 G2P の処理時間（目標 1% 未満）

| 経路 | 実測 | 分母 = 合成時間 | 分母 = 音声長 |
|---|---|---|---|
| **かな**（877 B のテーブル引き。本線） | **0.602 ms**（44 B → 53 ids）。⚠️ **QEMU の値**（[M-62](measurements.md#m-62)）で、**実機では単独に測っていない** | ⚠️ **比を出せない**（QEMU の G2P と実機の合成時間は混ぜられない） | 同左 |
| **漢字**（辞書 13.7 MB。`-DSAAN_KANJI=1` の追加経路） | **5.51〜66.30 ms**（**15〜84 B**）。[M-83](measurements.md#m-83)（33〜84 B / 27.85〜66.30 ms）と [M-90](measurements.md#m-90)（15〜48 B / 5.51〜40.79 ms）の合併。⚠️ **「約 0.8 ms/B の線形」は 33 B 以上の話**で、15 B では 0.37 ms/B（固定費の比率が上がる） | **1.1〜3.4% → ❌ 未達**（M-90 の 4 文。⚠️ **M-90 の表からの算術**） | **0.79〜2.3% → ❌ 未達**（M-83 で 1.7〜2.3%、M-90 で 0.79〜2.09%） |

⚠️ **「合成時間の 1%」は、合成が速くなったぶん逆に厳しくなった。** M-83 の時点では W8A32 で合成が遅く（xRT 4.28〜4.62）、
同じ G2P が合成時間の **0.5% 前後**で収まっていた。W8A8+PIE + S1〜S5b で合成が 10 倍近く速くなった結果、
**同じ絶対値のまま 1.1〜3.4% になった**。**分母が動く指標を要件にすると、速くするほど落ちる。**
⚠️ **G2P は RTF に 1 ms も寄与しない。** 効くのは「最初のチャンクが鳴るまでの遅れ」だけで、
そこは初回 pull が支配する（M-90 の同じ構成で **244.50〜244.66 ms**。漢字 G2P 5.51〜40.79 ms は
その **2.3〜16.7%**、かなは 1% 未満）。
**「1% 未満」という目安自体を絶対値（例: ≤ 50 ms）に置き換えるかは未決**（D-049 と同時に決める）。

### 6.3 品質

**評価は「教師比」で報告する。** 論文が多言語について
"absolute SCOREQ values are not calibrated for comparisons across languages" と
明言しているため。UTMOS も日本語では較正されていない。

**さらに「人間音声比」も併記する**（D-013）。UTMOS は日本語でスケールが圧縮されており、
**実人間の日本語音声ですら 2.305 しか出ない**（M-10）。天井を測らないと比が読めない。

```
教師 / 実人間 = 1.748 / 2.305 = 0.758   ← 現在地
```

| 指標 | 目標 | **実測（v3 / 2026-09-03）** | 備考 |
|---|---|---|---|
| SCOREQ（教師比） | **≥ 0.55** | ✅ **0.6444** [0.6044, 0.6843]（n=24。[M-61](measurements.md#m-61)） | 論文の英語 embedded は 2.54/4.68 = 0.5427。⚠️ `data_domain="natural"` は使わない（D-020） |
| DNSMOS OVRL（教師比） | （当初は項目に無い） | **0.7969** [0.7756, 0.8173]（M-61 / [D-034](decisions.md)） | ⚠️ 陽性対照 G6 が FAIL。**下がらないことを「劣化が無い」と読まない**（M-50） |
| UTMOS（教師比） | **≥ 0.63** | ⚠️ **主指標を SCOREQ に変えた**（[D-020](decisions.md)）ので、v3 では UTMOS 比を出していない | 論文の英語 embedded は 2.80/4.42 = 0.63 |
| UTMOS（人間比） | 参考値として併記 | 同上 | 教師/人間 = 1.748/2.305 = 0.758（M-10） |
| CER（かな） | 教師との差 ≤ 10 pt | ✅ **差 +0.0320** [−0.031, +0.087]、p=0.31（M-61） | ⚠️ **v2 → v3 で改善していない**（−0.0105 [−0.037, +0.018]） |
| 音素クラス別スペクトル平坦度（2–8 kHz） | 摩擦音で教師比 ≥ 0.85 | ✅ **1.0006**（fricative）/ 1.0153（affricate）（[M-40](measurements.md#m-40)、β=0、n=16） | ⚠️ **v2 の生徒で測った値**。v3 では測り直していない。⚠️ **SFM は必ず帯域内 RMS と併記する**（M-27） |
| アクセント型ミニマルペア | **聴取で**弁別可能 | ❌ **聴取ゼロ。** 教師との符号一致は 37/37 = 1.000（M-59）だが**聴取ではない** | ⚠️ chance は 0.5 ではない（経験的ヌル 0.614）。⚠️ `magnitude_ratio` 1.193 = 生徒の起伏が 19% 大きく、**過剰強調かは聴取でしか分からない** |

⚠️ **式7（摩擦音ノイズ注入）は不要だった。** β=0 で既に教師と一致しており、聴取でも β=0 に決めた
（[M-60](measurements.md#m-60) / [D-038](decisions.md)）。⚠️ **聴取者 1 名**で、v2↔v3 の差は 7 試行で聴き分けられなかった（C-037）。

## 10. 受け入れ条件

本プロジェクトが「成功した」と言える条件:

1. ✅ **ESP32-S3 実機**で中間表現から 22.05 kHz PCM が出る
   （**自分の M5Stack CoreS3 で確認**。checksum は QEMU と bit 一致。[M-82](measurements.md#m-82) / [M-90](measurements.md#m-90)。
   ⚠️ 第三者の独立報告も 2 件あるが、そちらは**未再現**）
2. ⚠️ **分母次第**。RTF ≤ 0.5 は**満チャンク 1 pull なら 0.446 で達成、発話全体なら 0.541〜0.712 で未達**（§6.2。**分母は未決 = D-049**）。
   RAM ピーク **157,360 B < 512 KB** ✅ / フラッシュ（モデル + G2P データ）**654,909 B < 1 MB** ✅
3. ✅ 浮動小数点参照との Pearson 相関 ≥ 0.98 → **1.000000**（[M-41](measurements.md#m-41)。論文と同じゴールデンテスト）
4. ✅ held-out セットで SCOREQ が**教師比 0.55 以上** → **0.6444** [0.6044, 0.6843]（n=24。[M-61](measurements.md#m-61)）
5. ✅ 音素クラス別スペクトル平坦度で、摩擦音が教師比 0.85 以上 → **1.0006**（[M-40](measurements.md#m-40)、β=0、n=16。⚠️ **v2 の生徒**で測った）
6. ❌ アクセント型ミニマルペアが**聴取で**弁別できる → **未。聴取はゼロ。**

**1 と 2 が満たせなければ、他がどれだけ良くてもプロジェクトの目的を達成していない。**

⚠️ **6 だけが人を待っている。** 5 は v3 で測り直していない（v2 の値）。
⚠️ **「符号一致 37/37」は 6 の代わりにならない**（それは教師との向きの一致であって、人が聴き分けられるかではない）。
⚠️ **ざっとした聴取は済んでいる**（M-91 / M-93 = 実機 / M-96 = ブラウザ。どれも**1 名・対照なし・盲検なし**）が、
**条件 6 が求めているのは対照つきの弁別**で、そちらは未実施。
checksum が一致しても、過剰強調（`magnitude_ratio` 1.193）・誤読・途切れは聴取でしか分からない。
